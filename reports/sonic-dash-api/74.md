## Source conclusions and caller coverage

### Generated APIs and shared Protobuf

[Root producer](https://github.com/sonic-net/sonic-dash-api/blob/4753c843f9459ec93051f5f5dd76350a41452cd1/BUILD.bazel#L1-L119) derives every generated C++/Python input from `proto/*.proto`. Public headers and separate source/module/stub output groups are declared. The selected Protobuf registry layer forwards to its Debian-prepared source and includes the actual `gen_pyi`/provider integration patch and path adapter.

`dashapi_objects` is `alwayslink=True`, preserving descriptors used by the unchanged utility implementation's name-based JSON resolver. Both DASH DSOs embed DASH's utility/generated objects, matching the old Make ownership pattern. The installed test therefore uses separate C-API and SWIG/Python processes rather than asserting that both descriptor owners can coexist in one process.

The selected Protobuf interface is a shared-only `cc_import`; `linkstatic=True` on DASH does not select a static Protobuf archive through that interface. Tests explicitly inspect `DT_NEEDED=libprotobuf.so.32`, the imported descriptor-pool implementation, selected loaded library paths, and installed runtime bytes. Those are authored acceptance predicates, not independently replayed runtime proof.

### Python and installed package layout

[SWIG/Python producer](https://github.com/sonic-net/sonic-dash-api/blob/4753c843f9459ec93051f5f5dd76350a41452cd1/misc/BUILD.bazel#L18-L125) uses explicit Python 3.13 headers and does not declare a libpython dependency. Generated modules/stubs are placed beside SWIG bindings. The unchanged package initializer explains existing plain sibling imports; no missing generated import rewrite was established.

The install table matches legacy directories for headers, shared library, Python package and CLI, with explicit modes. The source/installed tests derive schema inventory from actual inputs, check module descriptors and stub presence, and exercise optional fields, timestamps and CLI serialization. Stub presence is not a type-check or execution of `.pyi` files.

### Runtime/debug production and execution tools

The exact published Build Infra source, its version patch and relevant runtime implementations were inspected. The review reached the real strip script, debug transition, Make-base default, binutils/tool inputs, SWIG executable wrapper, private loader/runtime, GCC template/platform definitions, and ELF metadata parser—not only the test assertions or a manifest.

The strip path edits a writable ELF copy, applies the chosen RPATH policy before splitting, retains build-ID identity, compresses debug information where selected, and creates the runtime debuglink from the corresponding debug file. Macro/provider input propagation and the selected compiler/runtime helpers were read. No compiler, tool invocation, native import, target ELF execution or artifact extraction was performed by this review.

### Q1 — State ownership of non-ELF runtime requirements

[Runtime metadata call](https://github.com/sonic-net/sonic-dash-api/blob/4753c843f9459ec93051f5f5dd76350a41452cd1/BUILD.bazel#L184-L199) consumes the inherited Debian stanza with `shlibs`/`misc` substitutions, not `${python3:Depends}`. The pinned helper calls `dh_python3` only when such substitutions are required; ELF dependency analysis cannot infer Click or Python-Protobuf imports.

Documentation and CI explicitly supply Python 3.13, Click and Python-Protobuf. No supported downstream consumer omitting them was demonstrated. Clarify which layer owns these requirements; do not present generated shared-library controls alone as complete Python dependency closure.

### Q2 — Bind metadata authority to the deployed Protobuf provider

DASH deploys the separately source-built Protobuf runtime but analyzes dependencies against APT `libprotobuf32t64` data/control. The source-built module also exports `RuntimePackagesInfo`. Both selections intentionally use the same Protobuf/Debian version, and no present symbol or control mismatch was established.

Prefer the deployed provider's metadata, or explicitly document/validate the reference-provider equivalence. This is a maintenance/ownership question, not a proved ABI failure or a mandatory dependency upgrade.
