## Summary

This PR adds parallel native AMD64/ARM64 Bazel source builds and runtime/debug TARs for OpenSSL, SymCrypt core/provider, OpenSSH clients and Kerberos crypto libraries. The declarations model source-built dependency ownership, compiler/toolchain separation, original vendor test paths, target package metadata and split-symbol integrity.

The existing SONiC FIPS-mode/provider/logging/crypto-selection patches are refreshed to new source context. Their substantive policy is already present at BASE; no newly introduced crypto-policy weakening was grounded. Some exact composed Debian inputs remain unmaterialized, so the review does not claim byte-exact post-apply equality merely from patch headers.

All five archived fork workflows succeeded on both native architectures. Independent Git-tree comparison confirms their archived source tree equals current HEAD. Those historical external executions are applicable evidence, not fresh current-head or reviewer-executed native results.

## Source and ownership assessment

### OpenSSL source and build configuration

[Source preparation](https://github.com/sonic-net/sonic-fips/blob/b95dbbabb54c49f08a7630d9434df5ef4a4e39e7/openssl/sources.bzl) selects OpenSSL3.5.7 and Debian `3.5.7-1~deb13u3` by integrity-bound archives. It applies the SONiC series, Debian series, retained test patches and the build-info patch in the declared order, then derives the SONiC changelog version.

[The shared build contract](https://github.com/sonic-net/sonic-fips/blob/b95dbbabb54c49f08a7630d9434df5ef4a4e39e7/openssl/build.bzl) centralizes algorithm/configure flags, selected native platform/libdir, declared Perl and build timestamp. Runtime packages include the selected shared libraries, engine plugins, commands/scripts/configuration and development outputs. Ordinary package checks and the separately supplied SymCrypt vendor integration remain distinct.

The full BASE/current runtime patch bodies and relevant OpenSSL initialization/provider/engine source were inspected. RUN_ONCE FIPS detection, thread-local re-entry guards, optional provider preference and engine initialization are inherited policy—not automatically new defects from refreshing context. Existing error/availability limitations were not promoted into blockers without an additional supported consequence attributable to this diff.

### SymCrypt sealed runtime and provider

[Core/provider declarations](https://github.com/sonic-net/sonic-fips/blob/b95dbbabb54c49f08a7630d9434df5ef4a4e39e7/symcrypt/BUILD.bazel) preserve the selected upstream core103.8.0 and provider revision. The core scopes Clang; the provider retains GCC. Declared assembly/compiler/strip/archive tools and target/runtime library ownership were traced through the actual upstream and selected foreign-build implementations.

The core extracts symbols and computes its integrity digest before packaging. [The sealed-runtime wrapper](https://github.com/sonic-net/sonic-fips/blob/b95dbbabb54c49f08a7630d9434df5ef4a4e39e7/symcrypt/sealed_runtime.bzl) forwards the sealed core unchanged and attaches its existing debug tree. Provider/engine ELFs use the normal splitter. This avoids resealing or modifying the core through later generic RPATH/debuglink edits.

The authored package test checks installed core equality, startup loading, a disposable integrity-digest tamper, provider/engine digests and original core tests. These are meaningful predicates, not reviewer-executed crypto results or exhaustive integrity certification. The ARM64 `libatomic.so.1` dependency is explicitly modeled with target metadata; no actual ELF or archive was replayed here.

[Provider reproducibility](https://github.com/sonic-net/sonic-fips/blob/b95dbbabb54c49f08a7630d9434df5ef4a4e39e7/tools/bazel/provider_repro.py) compares unstripped provider/engine bytes including DWARF across two fresh output bases and an uncached CMake action. It does not promise identical whole TARs or random-key-bearing core bytes across independent builds.

## Nonblocking notes

### N1 — Refresh delivered integration and dependency/build-metadata descriptions

[OpenSSL README](https://github.com/sonic-net/sonic-fips/blob/b95dbbabb54c49f08a7630d9434df5ef4a4e39e7/openssl/README.md) still describes full provider-suite integration as pending and names older Distroless/Build Infra versions. The actual `MODULE.bazel` selects `.26` and Infra `.45`; the dedicated [integration target/workflow](https://github.com/sonic-net/sonic-fips/blob/b95dbbabb54c49f08a7630d9434df5ef4a4e39e7/openssl/integration/README.md) is present. Core `tools/bazel/ci.py` should say that this separate check is not run by that job, rather than implying its producer remains unavailable.

[SymCrypt README](https://github.com/sonic-net/sonic-fips/blob/b95dbbabb54c49f08a7630d9434df5ef4a4e39e7/symcrypt/README.md) names an older Binutils toolchain, first treats the build timestamp as variable and later documents its fixed epoch, and attributes the random integrity key to a generated include that contains version/debug definitions. Identify the separate integrity postprocessor and distinguish the fixed timestamp from random-key variation. These are documentation corrections, not changes to crypto policy.

### N2 — Retain the curated hidden resolution inputs

[Resolution producer](https://github.com/sonic-net/sonic-fips/blob/b95dbbabb54c49f08a7630d9434df5ef4a4e39e7/tools/bazel/ci.py#L46-L57) copies `.bazelrc` and `.bazelversion` to its artifact directory and records their hashes. Four workflows—Kerberos, OpenSSH, OpenSSL and OpenSSL/SymCrypt integration—use the upload action’s default hidden-file exclusion. Only the SymCrypt workflow enables hidden-file retention. Historical console input records corroborate this distinction.

The nonhidden declared/effective configuration and committed inputs mitigate the loss; it does not show a production failure or loss of every resolution receipt. Use explicitly named nonhidden copies, or allow hidden files only in the inspected curated artifact directory. Do not broaden collection to arbitrary workspace/credential files. This can follow separately.

### Q1 — Preserve an actual selected copy-patch outcome receipt

`openssl/sources.bzl::_apply_debian_patch` materializes Git-copy destinations and rewrites patch headers before applying them. Its first-section/preamble and mode assumptions should be checked against the actual selected Debian copy sections. Those exact archive inputs/composed results were not materialized in this review.

No constructed hypothetical patch is presented as a demonstrated failure of the selected series. Keep an owner validation/source receipt for those transformations if exact Make/quilt equality is claimed; a new archive/native campaign was not performed here.

### Q2 — Qualify ordinary-mode preconditions

`openssl/integration/ci.py` checks for `/etc/fips/fips_enable`, while the inherited runtime patch also recognizes `/proc/cmdline` `fips=1` and `sonic_fips=1`. On an arbitrary runner, absence of the file alone is not proof of ordinary mode.

No failure on the specified hosted runners was established. Document their assumption or record/check the effective activation conditions, without changing host state. This is a nonblocking portability/evidence suggestion.
