## R1 — consumer compatibility is checked after injections have already occurred

**Actual changed caller:** [test_leak_injection_sim.py main](https://github.com/sonic-net/sonic-buildimage/blob/fc8c24f01c4c3c3706957103226d0a7cd5ac3b73/platform/aspeed/sonic-platform-modules-nexthop/common/scripts/test_leak_injection_sim.py#L280-L339) runs `check_sensor_cycle` for each sensor, `check_clear_all` and `check_cli` **before** `check_state_db`.

[check_sensor_cycle](https://github.com/sonic-net/sonic-buildimage/blob/fc8c24f01c4c3c3706957103226d0a7cd5ac3b73/platform/aspeed/sonic-platform-modules-nexthop/common/scripts/test_leak_injection_sim.py#L121-L157) writes both default and CRITICAL injection markers. [check_state_db](https://github.com/sonic-net/sonic-buildimage/blob/fc8c24f01c4c3c3706957103226d0a7cd5ac3b73/platform/aspeed/sonic-platform-modules-nexthop/common/scripts/test_leak_injection_sim.py#L212-L276) correctly refuses its own later injection when `test_leak` is absent, but that refusal is too late for the earlier shared-marker mutations. Without `--verify-db`, it never runs at all.

**Condition/consequence:** running the documented verifier on its default shared marker directory against a consumer that ignores test provenance can expose an injected CRITICAL state to real mitigation before the compatibility skip. The README says incompatible consumers cause the check to skip with nothing injected; the whole caller does not satisfy that statement. A final `clear_test_leaks` removes markers afterward but cannot undo an action already dispatched during an earlier cycle.

**Actual selected producer/consumer:** the candidate selects daemon commit `d3136e26e3d7acb1f72bb2a7478b5c39687515dd`. Its thermalctld calls health/leak/severity but ignores `is_test_leak`, publishing system CRITICAL without the test flag. Its enabled bmcctld default critical policy dispatches power_off without that distinction. A new runtime liquid-cooling decision enables that monitoring path on recognized liquid chassis. This source chain demonstrates exposure to a mitigation-dispatch path **when GPIO reads are healthy**, not a physical shutdown observation. The selected old kernel may lack the named lines and yield Fault instead, which the thermal consumer excludes from aggregation. The control does not prove that the all-selected-pin image can reach the healthy condition; a containing kernel with an older/incompatible daemon remains the specifically unsafe consumer combination the guard claims to refuse.

**Controls:** exact AST extraction of verifier `main`, with all injection/DB calls replaced by fake recorders, shows default/CRITICAL cycle calls and CLI mutation calls preceding the unsupported-consumer skip. Exact selected thermal/classifier source with a synthetic healthy injected CRITICAL sensor produces the unmarked aggregate and records power_off dispatch. The merged943 consumer skips a correctly marked test-control row and retains physical-leak action. No marker file, GPIO, Redis, BMC service or power operation was executed.

**Base and counterevidence:** the injection cycles existed before; this PR newly adds the guard and promises incompatible-consumer refusal while introducing automatic monitoring and the hardware-backed sensor path. The issue is incomplete enforcement of that new safety gate under the actual caller, not a demand to rewrite the platform test API or an assertion that every run dispatches a physical action. A genuinely private unwatched `--leak-test-dir` or compatible producer/consumer composition avoids the stated shared-marker unsafe-consumer condition. The private-directory option still constructs sensors with GPIO readers; it is not a hardware-free execution mode. A merged dependency alone does not establish the installed consumer, and a `test_leak` field by itself does not prove every required safety consumer participates.

**Smallest correction:** perform and validate the required consumer compatibility preflight before **any** shared marker write or injection cycle, or refuse runtime injection unless a private unwatched directory/compatible consumer is explicitly established. Keep the full physical-leak precedence and coherent sampling; add a whole-main call-order negative control, not only a guard test inside `check_state_db`. Correct the README's no-injection assurance until the whole caller enforces it.
