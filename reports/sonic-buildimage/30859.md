## What the response establishes

The target source has not changed. Its sole filter addition removes `switch-platform-init.service` from the generated BMC enablement list and masks it. The actual late image-extension caller supplies the filesystem root under `CONFIGURED_PLATFORM == aspeed`; this is role-scoped image construction, not a global CPU-architecture runtime mask.

The selected service requires database.service and is ordered after swss and rsyslog-config. Its initializer makes an unguarded checked command call to read `/sys/devices/virtual/dmi/id/bios_version`. **If that file is unavailable and the preceding stages succeed**, the exception stops the initializer before network-stack, OS, syslog-state and readiness publication. This supports the principal failure rationale in the response.

Physical assertions such as “every BMC boot fails” and “a BMC has no DMI” remain attributed platform observations, not independently reproduced here. Source ordering proves the consequence of missing DMI, not universal hardware absence or a particular boot race.

## The earlier writes must remain in the scope answer

[Selected initializer main](https://github.com/sonic-net/sonic-host-services/blob/7f82db29696ff4d6967a5067b92444da737f2bb8/scripts/switch_platform_init.py) executes:

1. Connect CONFIG_DB, STATE_DB and APPL_STATE_DB.
2. Write APPL_STATE_DB `PORT_TABLE:CPU` with NULL/NULL.
3. Populate version dictionaries, including installer/image operations.
4. Write `CHASSIS_INFO|chassis` firmware-version if build_version is present.
5. Write `SW_COMP_INFO|boot_loader` **name** and **parent**.
6. Read the DMI BIOS version; only afterwards write boot-loader version/type.
7. Publish network-stack, OS, syslog and readiness information.

Therefore, failing the DMI command does **not** imply that SW_COMP_INFO has no rows. A partial boot-loader row has already been created if earlier stages succeeded. CPU and potentially chassis-version writes precede it as well. The complete reply’s broad “masking removes no data” premise is not supported by that source ordering.

The defined `write_host_paths` method is **not called by main**. HOST_STATS/hostname/fully-qualified-name output is not merely a later write blocked by DMI; it was not executed by this unit’s main path even when DMI succeeds. That part of the original broad publication inventory is narrowed accordingly.

An inert control using only three AST-selected methods with record databases and a failing command stub confirms the pre-DMI CPU/chassis/boot-loader writes. It executes no real command, Redis, file, service or device operation.
