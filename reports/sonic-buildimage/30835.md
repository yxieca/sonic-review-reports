## Summary

The previous ASPEED first-boot service runs after systemd has already invoked generators. Creating machine.conf only there can therefore be too late for the platform-dependent generator. The PR installs an initramfs hook and local-bottom caller, copies the existing platform detection helper into the ramdisk, and permits path/log overrides so the helper writes the persistent host partition before systemd starts.

Valid existing `onie_platform` metadata is kept, while an empty/truncated file is regenerated. Detection uses `/proc/device-tree` with a firmware-tree fallback and preserves platform-specific precedence; Nokia model detection is added. The helper writes an adjacent temporary file, cleans it on exit, synchronizes and atomically renames it. A systemd service remains a best-effort fallback, not a replacement for successful early generation.

### Persistent `/host` exists before local-bottom on the loop image path

The exact initramfs-tools0.142 source invokes `mountroot` before `local_bottom`, and runs init-bottom scripts afterward. SONiC's [loopback mount patch](https://github.com/sonic-net/sonic-buildimage/blob/098c206073f16c8ed0bbd177f09c8a8e1ce74eb4/src/initramfs-tools/loopback-file-system-support.patch) moves the backing partition into `${rootmnt}/host` during `mount_loop_root`. The image recipe creates the required `/host` directory to trigger this move.

The later union-mount runs in **init-bottom**, not local-bottom. It therefore does not imply that this new local-bottom script runs before the persistent host partition exists. The earlier potential ordering concern was checked against actual mount and install callers rather than filename order intuition.

These source facts support the normal SONiC loop-image flow. They are not a claim that every unsupported root layout or installation method was booted successfully. When `/host` or the helper is missing, the caller intentionally exits; a supported installation must supply that contract.

### Correct generator input and preserved baseline

[systemd-sonic-generator](https://github.com/sonic-net/sonic-buildimage/blob/098c206073f16c8ed0bbd177f09c8a8e1ce74eb4/src/systemd-sonic-generator/systemd-sonic-generator.cpp) opens `/host/machine.conf` for platform selection. The new early write targets that persistent file before generator execution. Late service ordering before sonic.target alone cannot repair an already failed generator; the early path is the meaningful fix.

The [helper](https://github.com/sonic-net/sonic-buildimage/blob/098c206073f16c8ed0bbd177f09c8a8e1ce74eb4/platform/aspeed/aspeed-platform-services/scripts/sonic-machine-conf-init.sh) first retains a file containing a nonempty `onie_platform=` value, avoiding overwriting installer-provided identification. Empty/truncated metadata is regenerated using the actual DT compatible/model values. The existing platform selection remains narrow rather than being generalized to unrelated hardware.
