## Summary

The shared-layer refactor keeps pluggable APIs/transport separate from CPO media while giving CPO ports bank-specific OE and shared ELS objects. The platform source explicitly limits this PR to link-up. Firmware locking/management and VDM freeze support added by downstream30430 are not demanded here merely because those features exist later.

The current standalone image nevertheless needs a coherent selected consumer/API contract and physical-index mapping. Common755-related CPO base APIs are present in the selected common pin; that alone does not implement the platform ELS event hook expected by selected xcvrd. The new bank layout also changes the relation between SDK modules and front-panel indices. R1/R2 retain reachable event/coordinate integration concerns. The selected media-key consumer is also incompatible with CPO lookup (R4), and shared modular thermal enumeration loses its existing override (R5). The shipped INI remains inconsistent, but actual default selection prefers valid JSON; R3 is therefore narrowed rather than falsely presented as an unconditional wrong-device path.

## R1 — selected ELS consumer reaches an unimplemented platform hook

**A1.** The new chassis provides CPO objects/get_cpo, but does not override `get_elsfp_change_event`. Its selected common gitlink3374ab3a56036062ef05ce731e9133e79a03cab6 `ChassisBase.get_elsfp_change_event` explicitly raisesNotImplementedError.

**A2.** Selected daemons gitlink5c167586692c30d0b15655ea3c6d796f73bad841 starts `CpoStateUpdateTask` when cpo_obj_dict is nonempty, even independently of skip_cpo_mgr's manager gate. That task's `_get_port_change_event(timeout)` directly calls the platform hook. The inherited state task invokes it inside its worker; outer `run` catchesException and sets the daemon's shared main stop event.

**A3.** The standalone selected image can stop xcvrd on first CPO event polling rather than deliver ELS presence changes. Coordinator-only exact base hook, CPO consumer and outer worker source were exercised with fake identities/events: inherited hook raises NotImplementedError and sets main-stop; an implemented-hook control does not. This is an inert source control, not an executed daemon observation.

**B1.** The base's missing ELS hook is inherited; **exposing the new CPO object path to an already selected CPO consumer is this PR's new interaction**. It is not fair to demand every future platform feature, but this reachable consumer must be safely supported or gated. **B2.** Common755 may already have landed, and a downstream30430 implementation exists; neither puts that downstream hook into this PR before its own merge. The author explicitly confirms the downstreams will rebase after29725 merges, so they cannot be silently assumed co-deployed.

[Candidate CPO accessor](https://github.com/sonic-net/sonic-buildimage/blob/8f306a0d2dcd8d369d4364caa0a4cc30c56be761/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L621-L652), [selected base hook](https://github.com/sonic-net/sonic-platform-common/blob/3374ab3a56036062ef05ce731e9133e79a03cab6/sonic_platform_base/chassis_base.py#L1013-L1052), [selected consumer](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/cpo/cpo_state_task.py#L36-L40).

Smallest correction: implement the required ELS stream in the standalone scope or explicitly gate the selected consumer until the hook is present, preserving link-up and graceful lifecycle. Verify removal/reinsert and daemon liveness with the owning test team; no live operation was performed here. ## R2 — ASIC notifications retain SDK coordinates after adding banked physical ports

**A1.** `_create_port` constructs CPO ports with physical `index` independent of shared OE `sdk_index`; the service SFP physically at65 remaps sdk_index to16. `_asic_modules_dict` contains those objects. `get_asic_change_event` instead collects SDK indices and emits `str(sdk_index+1)`.

**A2.** The shipped16 OEs each contribute four CPO bank objects, all sharing module IDs0–15, plus the service SFP with module16. ASIC notification keys consequently collapse to1–17. `get_change_event` merges those into the SFP event stream. The selected SFP state task owns the physical service SFP65, not17; the CPO state stream separately expects ELS keys for its physical ports.

**A3.** An ASIC down/up event can miss the intended physical ports and notify unrelated/not-owned indices; specifically service physical65 becomes17. Target-specific extracted ASIC/base methods with synthetic state verify service17 is correct at base while service65 is absent from the candidate SDK-derived1–17 keys; the selected service ownership predicate rejects those keys. This is an inert source control, not a hardware transition experiment.

**B1.** SDK+1 was appropriate in the old one-SDK-module-per-port layout. The newly introduced bank objects/service remap break that equivalence, so this is an introduced interaction rather than merely a legacy formula. **B2.** SDK IDs must remain used for sysfs/cancel-wait access; substituting physical IDs everywhere would be wrong. Event IDs and hardware-access IDs need separate ownership.

[Immutable mapping](https://github.com/sonic-net/sonic-buildimage/blob/8f306a0d2dcd8d369d4364caa0a4cc30c56be761/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L430-L448), [ASIC output](https://github.com/sonic-net/sonic-buildimage/blob/8f306a0d2dcd8d369d4364caa0a4cc30c56be761/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L804-L830).

Smallest correction: build per-consumer event maps using actual physical indices while retaining SDK coordinates for module operations; ensure CPO/ELS events reach the appropriate stream and service SFP65 remains65. Add a64-bank+service ASIC-down/up delivery case. [Existing human thread](https://github.com/sonic-net/sonic-buildimage/pull/29725#discussion_r4679058893) credited, not duplicated.

## R4 — selected media-key lookup is incompatible with technology-separated CPO objects

**Kind / priority:** new selected-consumer interaction, P1. **Disposition:** open; newly identified. This is a link-up/daemon integration requirement, not a demand for downstream firmware management.

The standalone candidate deliberately stores CPO ports in `_cpo_list` and its [get_sfp accessor](https://github.com/sonic-net/sonic-buildimage/blob/8f306a0d2dcd8d369d4364caa0a4cc30c56be761/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L636-L653) returns no SFP object at a CPO position. It also adds nonempty CPO media-settings profiles.

The selected daemon's [media-key function](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd_utilities/media_settings_parser.py#L354-L418) still calls `platform_chassis.get_sfp(physical_port).get_xcvr_api()`. CpoStateUpdateTask inherits the initial-information/notification path, and its table helper inherits the [SI-update guard](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd_utilities/xcvr_table_helper.py#L322-L341), which permits a missing/default synchronization value without excluding CPO ports.

**Condition/consequence:** for a present, information-readable CPO port on a non-warm/non-fast initialization where notification is required, key construction dereferences `None`. Only ValueError is caught locally; the inherited outer worker exception handler sets the daemon's main stop event. This can precede the missing ELS event-hook failure in R1. Fixing the event hook alone does not repair this separate caller mismatch.

**Counterevidence/control:** already-notified and warm/fast guards avoid their respective cases. CPO separation is intentional and should not be undone. Coordinator-only extracted notification/key/guard source with in-memory fixtures produces AttributeError for CPO-None, reaches profile lookup for an SFP-object control and returns safely for an already-notified control. No actual database, platform API or EEPROM was used.

**Base comparison:** base CPO objects were returned through the SFP branch; this PR creates technology-separated objects and the new nonempty media configuration. The newly reached incompatibility is attributable to this source combination, not to later firmware features.

**Smallest correction:** align the selected media consumer with `common.get_port_device` or explicitly gate unsupported notification until a compatible path is selected. Preserve link-up and the new SFP/CPO separation; add a cold-start CPO notification regression with a healthy SFP control.

## R5 — shared thermal enumeration bypasses modular line-card aggregation

**Kind / priority:** introduced shared-platform dispatch regression, P2. **Disposition:** open; newly identified.

The changed [ThermalManager](https://github.com/sonic-net/sonic-buildimage/blob/8f306a0d2dcd8d369d4364caa0a4cc30c56be761/platform/mellanox/mlnx-platform-api/sonic_platform/thermal_manager.py#L39-L58) uses `get_all_ports()` instead of `get_all_sfps()`. ModularChassis overrides only the latter to aggregate line-card ports. The inherited new getter enumerates fixed-chassis local lists, bypassing that aggregation; the pinned platform factory actually selects ModularChassis for line-card platforms.

**Condition/consequence:** on a modular chassis not taking the liquid-cooling early return, the updater loses the line-card enumeration previously supplied by polymorphic dispatch. Exact extracted base/head initializer/enumerator controls with two synthetic line cards pass two ports at base and none at head. Readiness and updater boundaries are inert; no thermal device, native platform import or worker thread ran.

**Counterevidence:** SN6810-LD's existing liquid-cooling guard disables this updater, so no thermal incident on that target is alleged. This is a regression in shared Mellanox code changed by the refactor, not a requirement for downstream firmware/fault functionality.

**Smallest correction:** preserve modular aggregation with an appropriate `get_all_ports` override or keep the existing non-CPO enumeration path, and test actual subclass dispatch rather than mocking the new getter directly.


## Qualified nonblocking questions

**Q1 — JSON order.** `build_cpo_port_map` assigns sequential chassis indices to first-seen unique OE/ELS/bank tuples. Current shipped insertion order aligns with JSON physical indices, but identical associations reordered by name would remap devices. Actual extracted mapper controls confirm current64-bank mapping and service64→16, while same-association lexical reordering changes63 mappings. The parser/interface-data contract does not independently establish a permitted arbitrary regeneration order, so this is retained as a nonblocking topology-stability question rather than a falsely observed current-device failure. Use declared physical mapping or validate order when improving this path. [Existing thread](https://github.com/sonic-net/sonic-buildimage/pull/29725#discussion_r4679058922).

**Q2 — all-bank ASIC-ready poll registration.** The main normal polling subset isbank0, while ASIC-ready re-registration iterates all bank objects. Source establishes an inconsistent subset. Nonzero-bank objects normally remain Down under the bank0 initialization flow, so forced software-state fanout cannot be called an automatically reachable neighboring-port outage. Physical effects require the actual event/mode contract. Keep the [existing question](https://github.com/sonic-net/sonic-buildimage/pull/29725#discussion_r4674283730) without inventing a demonstrated outage.

Empty topology I2C paths are not a blocker: this platform derives vendor sysfs coordinates from SDK module/bank rather than consuming that field for EEPROM access. Missing EEPROM power/frequency guards are inherited from base SFP and remain a separate robustness concern, not a new blocker demanded from link-up scope. Full firmware/VDM support is explicitly downstream and is not required merely to satisfy a template.
