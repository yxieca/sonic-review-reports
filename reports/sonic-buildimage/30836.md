## Summary
The operator helper installs server certificate/key/CA at `/etc/sonic/credentials/{restapiserver.crt,restapiserver.key,restapica.crt}` and, with `--push-config`, writes those same paths to REDFISH|certs. CN-only generation becomes supported; both CSR and signing-extension producers already conditionally emit IP SANs and retain DNS SANs. Post-install requests use a SAN hostname with a separate transport destination rather than disabling TLS verification.

The immutable actual Redfish consumer is path-driven: load CONFIG_DB → check matching certificate/key → combine/copy into bmcweb locations → watcher/guard restage and restart. The `/etc/sonic` container mount exposes these destinations. Sequential replacement and failed request reporting are inherited; no new outage or authentication regression was established.

## Grounded nonblocking nit
**Make the no-push message distinguish file installation from activation.** `platform/aspeed/sonic-platform-modules-nexthop/b27/scripts/generate_certificates.sh:260–285` replaces credential files before printing `Not applied: --push-config not given`. When REDFISH|certs already points at the new shared paths, the actual `stage-credentials.sh::run_watch` consumes changed files even without a new CONFIG_DB write. Prefer “Files installed; CONFIG_DB not updated.” This is a low-severity wording clarification: the header already warns existing files are replaced, the completion message says config not pushed, and the wording/control flow predates this change. Not a claim that no-push installation is broken or should suppress the watcher.
