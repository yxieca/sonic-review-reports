## R1 — one stale bank can starve every other module indefinitely

**A1 — source condition.** `_report_banks_as_they_tick` creates `pending`/`seen` and only removes a bank when its heartbeat covers arrival. An existing stale row adds the bank to `seen` but leaves it pending. The “unpublished bank” shortcut cannot remove that seen stale bank. The loop's `Select.TIMEOUT` branch simply continues; there is no elapsed deadline or retry/defer boundary.

**A2 — actual owner/caller.** `_main_loop` pops one queue item and synchronously calls `_process_one` -> `_report_banks_as_they_tick`. It does not service another module until that call returns. `_sweep_if_due` runs only when the outer queue.get returnsEmpty, so it cannot rescue an inner bank wait. The end-of-item lane-code re-read is also after the blocked wait.

**A3 — consequence.** If moduleA has a stale existing heartbeat and no future publication, moduleB's interrupt remains queued and moduleB's direct lane-code read does not happen. All-module idle recovery is also starved. The first direct read forA may already have been reported; that does not reportB or make the system live. A1000ms individual select timeout bounds shutdown observation, **not** total reporting latency.

**B1 — baseline.** This worker/queue/freshness protocol is new in the last commit; the exact parent has no FaultIndicationTask. This is not a legacy polling finding imported from report20.

**B2 — controls/counterevidence.** Fresh preloaded snapshots, per-bank arriving ticks, missing rows once another bank is seen, exception isolation and explicit stop are handled. The authored tests cover those success/stop cases; none proves another module progresses while an existing stale row never advances. The new direct lane-code path preserves low latency only for the current work item, not later queued items.

[Immutable wait](https://github.com/sonic-net/sonic-buildimage/blob/bb9507f33c9f0b0bceeb7657a61847b679c8ed23/platform/mellanox/mlnx-platform-api/sonic_platform/fault_indication_task.py#L614-L671), [serial caller](https://github.com/sonic-net/sonic-buildimage/blob/bb9507f33c9f0b0bceeb7657a61847b679c8ed23/platform/mellanox/mlnx-platform-api/sonic_platform/fault_indication_task.py#L329-L443).

Smallest correction: bound the total bank wait and defer unfinished banks/work, or make pending waits incremental so other modules and scheduled reconciliation can progress. Preserve freshness and late-latch recovery, rather than simply treating stale data as fresh. Add two-module staleA/healthyB coverage plus a freshA control. No new scheduler, framework or hardware probe is required by this assessment.

[Existing human thread](https://github.com/sonic-net/sonic-buildimage/pull/30716#discussion_r4679066011) reports a simulated starvation case; it is credited separately from coordinator-only inert controls. Actual extracted serial-loop/wait methods with a stale-existing-row fixture keep moduleB queued through four bounded timeouts with no idle sweep; fresh-preloaded and fresh-delayed controls allow B to progress. No actual subscriber, DB, EEPROM or worker thread was used. No author reply/fix was present.

## R2 — setup-failed worker never becomes usable after DB recovery

**A1.** `FaultIndicationTask.run` catches exceptions from setup/map construction, logs and returns. Chassis `_ensure_fault_indication_task` constructs/starts only when its reference isNone; it never checks a failed/terminated worker or clears the reference.

**A2.** `_enqueue_cpo_fault_interrupt` calls ensure then queues into that retained worker's queue. Later interrupt dispatch uses exactly that path. The queue still accepts items even when the thread has exited; no consumer remains to process them.

**A3.** A transient STATE_DB connection/setup error can permanently disable fault reporting for the remainder of the daemon process. Later healthy DB availability does not restart/setup the retained object. Work accepted after failure accumulates without reporting.

**B1.** Both worker and chassis owner hook are new last-commit code; no existing retry is being silently removed. **B2.** Catching per-item errors inside the active main loop is useful but irrelevant to setup failure, which returns before that loop. Startup-before-first-interrupt enables sweeps only if startup succeeds. The existing lifecycle tests mock the worker constructor and assert start-once/reuse; they do not exercise setup-failure then recovery through the actual owner.

[Immutable run setup](https://github.com/sonic-net/sonic-buildimage/blob/bb9507f33c9f0b0bceeb7657a61847b679c8ed23/platform/mellanox/mlnx-platform-api/sonic_platform/fault_indication_task.py#L236-L254), [chassis owner](https://github.com/sonic-net/sonic-buildimage/blob/bb9507f33c9f0b0bceeb7657a61847b679c8ed23/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L894-L915).

Smallest correction: retry setup within the same worker with bounded backoff and stop handling, or explicitly recover a terminated worker while retaining its queued work. Do not silently drop queued faults or repeatedly start an already-running Thread. Add setup failure, DB recovery and a subsequent/pending interrupt case. [Existing human thread](https://github.com/sonic-net/sonic-buildimage/pull/30716#discussion_r4679066018) credited; the actual setup/run and owner/enqueue source were additionally exercised with fake DB setup and non-threaded start boundaries: setup failure followed by healthy availability retains one object, one setup attempt and two unconsumed queued items, while an initially healthy control reaches processing. No native DB or thread operation was performed.

## N1 — shared ELS latches are widened more than once

**A1.** `_report_one_bank` keeps a watermark per bank row. Every ELS-scoped token from that row is emitted to **all bank_ports**. `_fan_out_xcvr_fault` writes/logs each split even if the token already exists; its union deduplicates stored text, not writes/warnings.

**A2.** Actual selected daemon source5c167586692c30d0b15655ea3c6d796f73bad841 CpoDomInfoUpdateTask reads a shared ELS snapshot once and publishes its ELS flag categories for each physical bank's first logical row. Its DBUtils updates `_SET_TIME` metadata and then writes flags plus `last_update_time`. The source comment claiming these ELS fields live only on bank0 is therefore not the selected producer contract.

**A3.** The same shared ELS latch can be read from four bank rows and widened four times to the same eight default breakout ports:32 per-token warnings/writes instead of8. Stored token union remains correct, so this is calibrated **nonblocking P3 diagnostic/efficiency** rather than claiming loss of the underlying fault. The human's numeric simulation result is attributed; coordinator-only exact parser/fanout methods with an in-memory table additionally produce32 writes for8ports, zero new writes for the same per-bank latch watermark and32 on a distinct latch. This is an inert source control, not an authored pytest or native DB test.

**B1.** Widening/watermark/emission is new last-commit code. **B2.** Per-bank watermarks are necessary for bank-local faults and later distinct latches; a blanket “already in cumulative token string” suppression would incorrectly suppress a new latch of the same condition. Fix scope-aware latch deduplication or avoid unnecessary second widening without losing relatches.

## R3 — failed publication is acknowledged before delivery succeeds

**Kind / priority:** new last-commit reporting-recovery defect, P2. **Disposition:** open; distinct newly identified concern, not already raised in the current three target threads.

The complete [_report_one_bank](https://github.com/sonic-net/sonic-buildimage/blob/bb9507f33c9f0b0bceeb7657a61847b679c8ed23/platform/mellanox/mlnx-platform-api/sonic_platform/fault_indication_task.py#L701-L735) updates its per-bank watermark immediately after parsing, **before** `_catch_up_on_causes` and `_emit`. The [parser](https://github.com/sonic-net/sonic-buildimage/blob/bb9507f33c9f0b0bceeb7657a61847b679c8ed23/platform/mellanox/mlnx-platform-api/sonic_platform/xcvr_fault.py#L165-L196) suppresses a later read of the same timestamp.

**Condition/consequence:** if a status-table read/write or another publication step fails after that watermark update, the existing per-item exception handler logs and moves on, but subsequent interrupts and idle sweeps treat the failed latch as already accounted for. A bank-local temperature latch can remain completely unpublished; a failure after writing the first breakout split can leave the second split missing its token. The error containment prevents a worker crash, but does not make delivery recoverable.

**Actual caller/control:** the interrupt path and `_sweep_one_vmodule` both call `_report_one_bank`. Coordinator-only extracted source controls preserve the real parser/watermark/fanout methods while replacing the database with an in-memory table: successful publication reaches both splits; an injected first read failure leaves no token and same-latch replay makes zero table calls; an injected second-split write failure leaves one split and replay again performs no publication. These are inert source controls, not native Redis failures or an authored test-suite run.

There is a related [lane-code sweep limitation](https://github.com/sonic-net/sonic-buildimage/blob/bb9507f33c9f0b0bceeb7657a61847b679c8ed23/platform/mellanox/mlnx-platform-api/sonic_platform/fault_indication_task.py#L570-L593): it checks only the lead logical port. If that destination was written before another destination failed, a later sweep sees the lead token and does not repair the remaining split. The same in-memory partial-fanout control verifies that branch.

**Base/scope:** watermark acknowledgement and these sweep-delivery rules are new in the last commit; this is not reopening a parent transport robustness issue. The source proves loss under the stated recoverable failure condition, not the frequency of real database faults.

**Smallest correction:** advance the watermark only after successful publication, or retain explicit pending delivery for failed destinations. Reconcile lane-code delivery per destination rather than using one lead-port success as whole-vModule completion. Add failed read, mid-fanout failure, same-latch retry and successful-write controls without suppressing later distinct latches.

## Q1 — recovery startup when optional interrupt nodes are unavailable

**Nonblocking source-contract question.** Initial registration deliberately omits a missing optional interrupt node while preserving presence descriptors. However, the chassis starts the fault worker only when a registered interrupt descriptor is present; the independent sweep cannot run if all such descriptors were unavailable at startup. A later refresh can register a newly available node, and a later nonzero interrupt can start the worker, but quiet recovery does not itself guarantee either event.

This is a conditional startup/recovery gap in the new source, not proof that supported hardware actually presents late/missing nodes. Could the owner confirm whether supported initialization guarantees at least one interrupt node, or start/reconcile the sweep from initialized CPO topology independently of node availability? Preserve the useful optional-node presence fallback. Without the hardware/readiness contract, this is not promoted to a separate blocker.


## R4 — selected ELS case-temperature flags are labeled as custom-monitor faults

**Kind / priority:** new selected-producer/consumer semantic mismatch, P2. **Disposition:** open; distinct separate SME finding, independently grounded; not already raised in the current target threads.

The new [token dictionary](https://github.com/sonic-net/sonic-buildimage/blob/bb9507f33c9f0b0bceeb7657a61847b679c8ed23/platform/mellanox/mlnx-platform-api/sonic_platform/xcvr_fault.py#L101-L110) maps `temperature_alarm_high/low` and `temperature_warn_high/low` to `xcvr_cpo_els_custom_mon_*`, with a comment describing byte11's custom-monitor nibble.

At the selected common revision, however, [get_non_banked_elsfp_dom_flags](https://github.com/sonic-net/sonic-platform-common/blob/3374ab3a56036062ef05ce731e9133e79a03cab6/sonic_platform_base/sonic_xcvr/api/public/elsfp.py#L666-L683) derives those exact fields from **byte9's low-nibble case-temperature flags**. The selected NVIDIA API and memory-map classes are empty subclasses; neither supplies the asserted custom-monitor projection. The selected daemon publishes those ELS fields and their set-time metadata to the rows consumed by the new worker.

**Condition/consequence:** a case-temperature latch from that selected producer is reported under a different monitor's fault token. Matching field names prevent a lookup failure, but do not make the token's meaning correct. This also does not establish coverage of the intended byte11 custom-monitor condition.

**Control/counterevidence:** coordinator-only extracted producer and token-parser source, with fake byte values0/1/2/4/8, returns no fault for0 and custom-monitor high/low alarm/warning tokens for the four byte9 case-temperature bits. The vendor subclass bodies were inspected for overrides. No physical EEPROM was read. This is a selected-source semantic mismatch—not proof about the actual hardware's custom-monitor wiring. An intended future producer revision must be pinned and inspected rather than assumed installed.

**Base/scope:** the producer's case-temperature contract is preexisting; interpreting it as custom monitor is introduced by the last commit's fault-token mapping.

**Smallest correction:** label these producer fields with their actual case-temperature meaning. If custom-monitor reporting is required, expose a distinct producer field with the intended register projection and align the selected dependency. Add a producer-to-token regression, not only an assertion of the consumer's own dictionary.
