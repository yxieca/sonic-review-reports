## Summary

The platform separates pluggable and CPO lists while retaining chassis physical indexing; CPO ports expose OE/ELS devices with shared module coordinates and bank-specific APIs. The new source transport keeps unbanked page FFh distinct from banked offsets, page0 at bank0, EIO-only retries and length/error return contracts. Per-module firmware serialization surrounds the full ELS generator lifetime; OE firmware mutation is explicitly unsupported. Thermal naming now uses chassis position, preventing the four OE banks from colliding. The supplied topology consistently represents64 OE banks from16 OEs, with one service module and128 default front-panel logical rows plus two service rows.

Those source improvements do not establish a working selected image. The exact common gitlink lacks the newly imported CDB lock module and firmware mixin support. The independent ELS poller also violates its new timeout contract and never updates its descriptors after control-mode changes. Existing human threads already identify R1–R3. The full review additionally identifies physical/SDK event-key mismatch (R4), a selected media-settings consumer incompatibility (R5), order-dependent ELS removal handling (R6), and shared modular thermal enumeration loss (R7). It preserves existing discussions rather than duplicating their feedback.

## R2 — preserve caller deadline separately from blocking poll slices

[A1: new ELS loop](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L1251-L1330) records `wait_forever=(timeout==0)` then overwrites timeout with at most1000ms. With0, it repeatedly calls `poll(0)` and never exits on elapsed time. With5000, it polls1000 and compares elapsed time to the overwritten1000, returning empty after about one second rather than preserving5000.

A2: selected daemons gitlink5c167586692c30d0b15655ea3c6d796f73bad841 `CpoStateUpdateTask._get_port_change_event(timeout)` passes its timeout to this method and consumes `elsfp`/`elsfp_error`. Its inherited state-task loop uses finite polling intervals; **not every xcvrd call is asserted to use0**. The documented public method explicitly allows0 indefinitely and arbitrary finite milliseconds, so both cases remain in scope.

A3: callers requesting an indefinite no-event wait consume CPU instead of blocking; long finite caller waits are shortened. B1: analogous timeout capping already exists in the base's separate SFP event methods. This report does not reopen those legacy methods as new defects; the ELS API is newly added and carries the same mistake into its explicit contract. B2: a small finite timeout works, and shutdown-friendly short poll slices are useful; neither justifies discarding the overall deadline.

Smallest correction: retain the requested timeout/deadline, choose a positive bounded blocking slice for indefinite waits and the smaller remaining slice for finite waits, and check shutdown without busy-polling. Add source tests for0 and a5000ms no-event wait. Current ELS tests use1ms and do not cover either branch.

Existing [zero-timeout thread](https://github.com/sonic-net/sonic-buildimage/pull/30430#discussion_r4663246155) and [finite-timeout thread](https://github.com/sonic-net/sonic-buildimage/pull/30430#discussion_r4663319773), including [human follow-up](https://github.com/sonic-net/sonic-buildimage/pull/30430#discussion_r4679061460), remain unresolved. Coordinator-only inert extraction of the actual method used fake clock/poll inputs:0 repeatedly polls0,5000 returns at1000, and1/1000 controls preserve their requested intervals. No real poller, signal or daemon was used.

## R3 — independent ELS descriptors must follow actual mode transitions

A1: `_register_els_fds` picks descriptors with `ModuleDetectionFlow.get_fds_for_poling(port)` once; `get_elsfp_change_event` only registers when its poll object is absent. The selector uses `present` under FW control versus `hw_present` and `power_good` in other modes.

A2: main `get_change_event_for_module_host_management_mode` drives module transitions and calls `ModuleDetectionFlow.refresh_poll_obj` with **self.poll_obj/self.registered_fds**. The ELS poll object and registered-fd dictionary are separate; that refresh does not modify them. Each get_fd opens an independent descriptor, so keeping poll objects separate is correct and must be preserved.

A3: after an actual FW-to-SW transition, the main stream can move to hardware-presence/power nodes while ELS continues watching the old `present` node. The new ELS stream can miss the nodes it promises to monitor until restarted/reset. B1: the separate ELS stream is new; this is not an inherited SFP refresh defect. B2: fixed-mode events, initial dummy suppression, bank0 registration and per-bank fanout are covered by the new tests; none changes control mode between registrations. Actual selector and refresh methods were additionally exercised with fake descriptors: the main stream changes to hw_present/power_good while the independently owned ELS stream remains present. This is an inert source control, not an observed physical hotplug failure.

[Immutable registration/loop](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L1172-L1330) and [main refresh caller](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L987-L1034).

Smallest correction: reconcile each ELS subscription with current mode at a safe owner boundary, retaining independent poll/FD ownership and preserving dummy-event handling. Add a mode-transition then ELS-event case without restarting the daemon. Existing [human thread](https://github.com/sonic-net/sonic-buildimage/pull/30430#discussion_r4679060340) credited; do not repost it.

## R4 — ASIC events use SDK addresses after the new physical/SDK remapping

**Kind / priority:** introduced interaction regression, P2. **Disposition:** open; newly identified, not already raised as this distinct issue in the current discussion.

The candidate's [_create_port](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L431-L452) maps four CPO banks onto one SDK module and maps the service SFP's physical index65 onto SDK module16. However, [get_asic_change_event](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L840-L867) still emits `sdk_index + 1` as the externally visible event key.

**Condition/consequence:** on an ASIC readiness transition, the supplied topology generates keys1–17 rather than physical identities1–65; the service SFP's event is keyed17 rather than65. The [selected ordinary state task](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd.py#L604-L622) rejects events outside its owned physical-port dictionary. Its service-port task therefore misses that ASIC transition under the correct identity. CPO state uses the separate ELS stream; this finding does not assume the ordinary SFP task should accept CPO events.

**Base and counterevidence:** the arithmetic is inherited, but the new shared-OE/service remapping invalidates its former identity assumption. Ordinary module-event paths already use `s.index`, and SDK IDs remain correct for sysfs operations and reset-wait cancellation. Exact extracted head/base methods with their respective synthetic module coordinates both generate17 SDK-derived keys. Base service physical17 is represented correctly; the new service physical65 is not. The actual consumer predicate rejects every head key for a service65-only dictionary. These are inert source controls, not a physical ASIC-flap test.

**Smallest correction:** generate event keys from physical port identities and explicitly route CPO ASIC notifications to their consuming stream, retaining SDK indices only for module operations. Add an ASIC down/up regression covering service port65 and shared CPO module coordinates.

## R5 — the selected media-settings caller is incompatible with CPO `get_sfp()` separation

**Kind / priority:** introduced cross-repository consumer incompatibility, P1. **Disposition:** open; newly identified.

The new [get_sfp contract](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L672-L689) correctly returns no SFP for a CPO position. The selected daemon's [get_media_settings_key](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd_utilities/media_settings_parser.py#L354-L418) and `get_lane_speed_key` still call `platform_chassis.get_sfp(physical_port).get_xcvr_api()`.

**Reached caller:** CpoStateUpdateTask inherits the [initial information/notification loop](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd.py#L385-L409). On a present, readable CPO port during non-warm/non-fast initialization, it can call `notify_media_setting`. The actual [SI-update gate](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd_utilities/xcvr_table_helper.py#L322-L341) permits notification when the saved sync-status value is absent/default; the CPO helper does not override it.

**Condition/consequence:** when that gate permits notification, the selected parser dereferences `None` **before** it evaluates the new profile's service-only `65-65` selector. Its `except ValueError` does not contain AttributeError. The inherited [worker exception boundary](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd.py#L733-L743) records the exception and signals the daemon's main stop event.

**Base and counterevidence:** base CPO objects were returned through `_sfp_list/get_sfp`, and this SKU lacked the nonempty media-settings file. The separation is intentional and should not be undone. Already-notified and warm/fast-reboot guards avoid this path; the selector itself also correctly accepts only service65. None protects an eligible CPO caller before key construction. Inert execution of the actual notification/key functions gives AttributeError for a CPO-None fixture, reaches profile selection for an SFP-object control, and returns without error for an already-notified control. No daemon or database was started.

**Smallest correction:** align the selected daemon's media-key lookups with `common.get_port_device`, or reject unselected ports before device/API lookup. Include the correction in the dependency combination and add a cold-start CPO-plus-service-media regression. Updating only the missing common CDB module in R1 does not resolve this separate consumer incompatibility.

## R6 — ELS absence can be overwritten by power-good processing in the same batch

**Kind / priority:** new event-reconciliation defect, P2. **Disposition:** open; newly identified.

The [independent ELS loop and status mapper](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L1239-L1326) translate each descriptor independently into the same four bank entries. After initial dummy events are consumed, a batch containing `hw_present=0` followed by `power_good=0` first records removal, then overwrites it with inserted-plus-power-budget-error (`5`). Reversing the same two notifications produces removal (`0`).

**Reached consequence:** selected CpoStateUpdateTask consumes this dictionary. Its inherited [removal branch](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd.py#L655-L677) clears APIs/deletes port data; inserted/error processing does not perform equivalent removal cleanup. Final state therefore depends on input order, not just the observed absence.

**Base and counterevidence:** this stateless ELS translation is new; the ordinary detection flow uses state/presence-aware filtering. A power drop while the module is still present legitimately produces a power error and must remain supported. Inert exact-loop controls return5 versus0 for the two orders, with removal-only and present-power-drop controls retained. The source permits this input sequence; no claim is made that hardware always emits it, how often it occurs, or in which order.

**Smallest correction:** reconcile each virtual module's observations before publication, giving confirmed absence precedence, or publish a coherent detection-state snapshot. Cover both orders and events split across calls without losing legitimate present-module power errors.

## R7 — thermal enumeration loses the modular chassis override

**Kind / priority:** introduced shared-platform dispatch regression, P2. **Disposition:** open; separate SME finding confirmed by coordinator grounding.

The changed [ThermalManager.initialize](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/thermal_manager.py#L39-L58) calls `get_all_ports()` instead of `get_all_sfps()`. [ModularChassis](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L1976-L1993) overrides only `get_all_sfps()` to aggregate line-card ports. It inherits `get_all_ports()`, which enumerates fixed-chassis local lists rather than that module aggregation. The pinned platform factory selects ModularChassis when line cards are present, and the inherited thermal-manager accessor exposes this manager.

**Condition/consequence:** on a modular chassis that does not take the liquid-cooling early return, the updater loses the line-card list previously provided through polymorphic dispatch. Exact extracted initializer/enumerator controls with two synthetic line cards supply two ports at base and none at head; readiness/updater boundaries are inert. This demonstrates dispatch loss, not a physical thermal incident or a full modular initialization test.

**Counterevidence:** SN6810-LD has leak sensors and takes the existing early return, so this is not asserted as an outage on that liquid-cooled target. It is a regression in the shared Mellanox implementation changed by the PR. The authored manager tests mock `get_all_ports` directly and do not exercise ModularChassis.

**Smallest correction:** preserve modular aggregation with an appropriate `get_all_ports` override or retain the existing non-CPO enumeration path; add an actual subclass-dispatch regression.


## Nonblocking questions and excluded overclaims

**Q1 — unknown power rating.** New `get_module_max_power` returns invalid on missing EEPROM bytes; `check_power_capability` returnsFalse, the state machine enters Exceed Power Limit and powers off/resets the module. The base dereferenced missing bytes and could throw instead. The new fail-closed safety behavior is reasonable; no requirement to power an unknown-rated module is invented. The shared label/error is diagnostically ambiguous and retry/recovery is not explicit (stable state accepts power-good or removal events). Preserve the [human recovery question](https://github.com/sonic-net/sonic-buildimage/pull/30430#discussion_r4679060369); it is not promoted to an unsafe-power blocker.

**Q2 — ASIC-ready bank dedup.** Normal polling uses only bank0, but `_enable_polling_for_asic` iterates `_asic_modules_dict`, which includes all CPO banks. Static source proves re-registration can bypass that dedup invariant. Nonzero-bank objects normally remain Down under the bank-zero initialization flow, and undefined state events do not automatically reach stable-state fanout. A forced-software-state bank1 control generates keys2–5, but that fixture does not prove the asserted state is reachable after ordinary recovery. Physical consequences remain unverified. [Existing thread](https://github.com/sonic-net/sonic-buildimage/pull/30430#discussion_r4663582108) remains a qualification question, not a demonstrated outage. A consistent bank0 list would be the bounded remedy; no additional live preflight is demanded.

The empty `i2c_path` question is reconciled with the actual platform: `_NvidiaSysfsCpoDevice` derives paths from sdk_index/bank using the sx_core tree, rather than reading a topology I2C path. Empty metadata alone is not a grounded read failure. All selected64 bank mappings align with platform physical indices1–64, OE groups/banks and the service remap64→16. The three changed simx symlinks resolve to existing real-platform targets in the immutable Git tree. Their API contents endpoint returns dereferenced bytes, so source mode/link blobs were inspected separately.

No issue is inferred solely from classifier metadata advertising old Python versions, arbitrary vendor code availability, API latest-head assumptions, fake differing objects, or a hardware event that was not observed.
