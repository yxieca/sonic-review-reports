**Reached caller:** CpoStateUpdateTask inherits the [initial information/notification loop](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd.py#L385-L409). On a present, readable CPO port during non-warm/non-fast initialization, it can call `notify_media_setting`. The actual [SI-update gate](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd_utilities/xcvr_table_helper.py#L322-L341) permits notification when the saved sync-status value is absent/default; the CPO helper does not override it.

**Condition/consequence:** when that gate permits notification, the selected parser dereferences `None` **before** it evaluates the new profile's service-only `65-65` selector. Its `except ValueError` does not contain AttributeError. The inherited [worker exception boundary](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd.py#L733-L743) records the exception and signals the daemon's main stop event.

**Base and counterevidence:** base CPO objects were returned through `_sfp_list/get_sfp`, and this SKU lacked the nonempty media-settings file. The separation is intentional and should not be undone. Already-notified and warm/fast-reboot guards avoid this path; the selector itself also correctly accepts only service65. None protects an eligible CPO caller before key construction. Inert execution of the actual notification/key functions gives AttributeError for a CPO-None fixture, reaches profile selection for an SFP-object control, and returns without error for an already-notified control. No daemon or database was started.

**Smallest correction:** align the selected daemon's media-key lookups with `common.get_port_device`, or reject unselected ports before device/API lookup. Include the correction in the dependency combination and add a cold-start CPO-plus-service-media regression. Updating only the missing common CDB module in R1 does not resolve this separate consumer incompatibility.

## R6 — ELS absence can be overwritten by power-good processing in the same batch

**Kind / priority:** new event-reconciliation defect, P2. **Disposition:** open; newly identified.

The [independent ELS loop and status mapper](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L1239-L1326) translate each descriptor independently into the same four bank entries. After initial dummy events are consumed, a batch containing `hw_present=0` followed by `power_good=0` first records removal, then overwrites it with inserted-plus-power-budget-error (`5`). Reversing the same two notifications produces removal (`0`).

**Reached consequence:** selected CpoStateUpdateTask consumes this dictionary. Its inherited [removal branch](https://github.com/sonic-net/sonic-platform-daemons/blob/5c167586692c30d0b15655ea3c6d796f73bad841/sonic-xcvrd/xcvrd/xcvrd.py#L655-L677) clears APIs/deletes port data; inserted/error processing does not perform equivalent removal cleanup. Final state therefore depends on input order, not just the observed absence.

**Base and counterevidence:** this stateless ELS translation is new; the ordinary detection flow uses state/presence-aware filtering. A power drop while the module is still present legitimately produces a power error and must remain supported. Inert exact-loop controls return5 versus0 for the two orders, with removal-only and present-power-drop controls retained. The source permits this input sequence; no claim is made that hardware always emits it, how often it occurs, or in which order.

**Smallest correction:** reconcile each virtual module's observations before publication, giving confirmed absence precedence, or publish a coherent detection-state snapshot. Cover both orders and events split across calls without losing legitimate present-module power errors.

## R7 — thermal enumeration loses the modular chassis override

**Kind / priority:** introduced shared-platform dispatch regression, P2. **Disposition:** open; separate SME finding confirmed by coordinator grounding.

The changed [ThermalManager.initialize](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/thermal_manager.py#L39-L58) calls `get_all_ports()` instead of `get_all_sfps()`. [ModularChassis](https://github.com/sonic-net/sonic-buildimage/blob/97dd087f87423f1e31d5cd13c3ef371a620ccf4f/platform/mellanox/mlnx-platform-api/sonic_platform/chassis.py#L1976-L1993) overrides only `get_all_sfps()` to aggregate line-card ports. It inherits `get_all_ports()`, which enumerates fixed-chassis local lists rather than that module aggregation. The pinned platform factory selects ModularChassis when line cards are present, and the inherited thermal-manager accessor exposes this manager.

**Condition/consequence:** on a modular chassis that does not take the liquid-cooling early return, the updater loses the line-card list previously provided through polymorphic dispatch. Exact extracted initializer/enumerator controls with two synthetic line cards supply two ports at base and none at head; readiness/updater boundaries are inert. This demonstrates dispatch loss, not a physical thermal incident or a full modular initialization test.

**Counterevidence:** SN6810-LD has leak sensors and takes the existing early return, so this is not asserted as an outage on that liquid-cooled target. It is a regression in the shared Mellanox implementation changed by the PR. The authored manager tests mock `get_all_ports` directly and do not exercise ModularChassis.

**Smallest correction:** preserve modular aggregation with an appropriate `get_all_ports` override or retain the existing non-CPO enumeration path; add an actual subclass-dispatch regression.
