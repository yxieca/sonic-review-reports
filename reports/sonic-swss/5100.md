## Summary

The feature is well scoped: history is attached to genuine detection/restoration reports, storm numbering survives COUNTERS_DB resets, normal pruning includes interrupted records, software restoration commits traffic before recording it, and the previously reported hardware warm-initialization issue is fixed. One supported hardware reconfiguration path still omits a history termination boundary: a stormed TC removed from the watchdog mask can be successfully disabled without its retained record being marked interrupted.

R1 concerns the correctness of the new retained diagnostic history, **not a demonstrated forwarding outage or regression in hardware storm recovery**. Two general source lenses identified this path; the separate SME lens promoted its original question after reading the actual QoS producer and companion consumer. The third general lens was source-favorable and did not identify R1. The recommendation is therefore grounded synthesis with preserved dissent, not unanimous agreement.

## Blocking finding

### R1 — P2: Close history when a removed hardware TC is successfully retired

**Condition:** hardware watchdog watches TCs 3 and 4; TC 3 has a genuine detected storm. A valid `PORT_QOS_MAP` SET changes `pfcwd_sw_enable` from `3,4` to `4`, followed by a valid per-port `PFC_WD` SET with the same action and valid timers. The relevant queue disables succeed. The QoS SET alone is **not** claimed to restart the watchdog.

The [actual QoS handler](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/orchagent/qosorch.cpp#L2046-L2229) parses the watchdog mask separately from actual `pfc_enable` and saves it through the [PortsOrch setter/getter](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/orchagent/portsorch.cpp#L2586-L2621). Hardware [reconfiguration](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/orchagent/pfcwdhworch.cpp#L468-L490) consults the [current-mask storm guard](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/orchagent/pfcwdhworch.cpp#L1170-L1210), so the still-tracked TC 3 is skipped once its mask bit is removed.

[Successful teardown](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/orchagent/pfcwdhworch.cpp#L909-L995) finds TC 3 through the old queue mapping, commits/closes its COUNTERS_DB accounting, and erases its storm membership and mapping. Neither complete cleanup function writes a restoration/interruption to history. The new interruption is attached only to [initialization of the newly selected TCs](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/orchagent/pfcwdhworch.cpp#L1116-L1150), which now visits TC 4 rather than TC 3.

**Consequence:** TC 3 retains `storm_N_detected` without `restored` or `interrupted`, although its handling has ended. Subsequent RECOVERED processing cannot normally close it after its mapping is removed. The [merged companion history consumer](https://github.com/sonic-net/sonic-utilities/blob/7e5f65e17226a6bfb9f36838ea8fd915080ebfec/pfcwd/main.py#L232-L325) renders the record with `-` rather than `interrupted` and no terminal timestamp.

The row can remain open while that TC stays unregistered. **Later re-registration interrupts it before a new detection**, so this is not an inevitable merge of all later storms. That later write does not recover the actual earlier teardown timestamp. Unchanged-mask storm deferral, a genuine RECOVERED processed first, and successful configuration DELETE are valid controls: the first defers reconfiguration, the second restores history normally, and the third purges the rows. These controls do not cover the SET-only removed-TC sequence.

**Attribution:** mutable-mask guards, old-mapping teardown and counter closure already exist at BASE. This PR introduces the retained history and attaches interruption to initialization/software teardown, but not to this successful hardware retirement path. The finding does not reclassify inherited SAI behavior as a new hardware defect.

**Smallest correction:** after successfully disabling each tracked queue, interrupt its history using the saved port alias and TC before erasing that identity. Cover both teardown loops. Preserve tracking/open history when disable fails, and retain initialization interruption for warm-start records. Add a notification/configuration regression for `{3,4} → {4}` with TC 3 stormed, plus unchanged-mask, DELETE and disable-failure controls.

**Validation:** complete enclosing functions, actual callers, QoS producer, BASE attribution and consumer were inspected. This is a static source finding; no C++ evaluator, reproduction, live frequency or outage result is claimed.

## Nonblocking nits

### N1 — P3: Document the new schemas and last-event semantics

The [new definitions](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/orchagent/pfcwdcounters.h#L25-L52) call `PFC_WD_STATE` current state, but interruption updates only history and the [BRS test](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/tests/mock_tests/pfcwd_history_ut.cpp#L673-L688) intentionally expects `storm_detected` to remain. Merge-style detection writes also retain prior restoration/duration fields. Define these as last-event/last-completed-storm semantics if intended, and document optional fields, epoch microseconds versus duration milliseconds, interruption, depth, counter reset, cold construction and configuration purge in the [schema document](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/doc/swss-schema.md).

The actual companion history CLI reads `PFC_WD_STORM_HISTORY`, not the new `PFC_WD_STATE.status`; it already recognizes interruption. No current CLI misclassification from retained status is asserted. Reusing the existing delimiter constant is an optional consistency improvement; the present literal is correct.

### N2 — P3: Avoid a real-clock scheduling deadline in the duration test

The [new test](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/tests/mock_tests/pfcwd_history_ut.cpp#L304-L323) seeds detection approximately 500 ms before the real current clock, then requires duration ≤800 ms. Host descheduling between seed and restore can exceed that roughly 300 ms allowance despite correct production behavior. Inject a clock or compare stored detection/restoration timestamps with the documented millisecond conversion. This is a source-derived flakiness risk, not an observed CI failure or executed test result.

## Optional integrity question

### Q1 — P3: Define recovery from partially recorded events

[Detection/restoration](https://github.com/sonic-net/sonic-swss/blob/ebb7de7807ecf97dc17c79f2aeeea3512087da9a/orchagent/pfcwdorch.cpp#L722-L830) use separate state/history/pruning commands. Each multi-field HSET is one command; there is no claim of partial field application within it. A failure between commands can leave inconsistent counts, an older open history record, or incomplete pruning. Later detection may interpret retained open history as replay. This is deliberately best-effort telemetry and ordinary recording exceptions are contained, so perfect durability is not imposed as a merge requirement. Clarify that limit or reconcile incomplete events if stronger history integrity is intended. No fault was injected; inherited SAI sampling failures are not a second newly introduced watchdog blocker.

## Grounding and dropped trail

- Preserved dissent: one general lens was favorable; R1 was retained by two general lenses and, after producer-context repair, the independent SME.
- “Always permanently open” and “all later storms merge” were narrowed: re-registration interrupts before a later detection, but cannot recover the earlier termination time.

- Hardware RX zeros and SAI-sampling limits are inherited egress-accounting behavior, not new history blockers. Duplicate notification counts, missing interrupted/mechanism pruning, whole-hash replacement and the already-fixed warm-init concern were contradicted by source.
