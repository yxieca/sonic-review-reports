## Summary

The PR adds native AMD64/Trixie Bazel packaging and tests around unchanged LLDP daemon source. The wheel preserves owner payload/version and the module entry, while external Common and `sonic-py-common` remain application-owned. The runtime TAR corrects wheel-ZIP file modes and supplies deterministic ownership/timestamps.

The installed fixture meaningfully checks owner/site paths and payload/metadata, then separately tests entry dispatch and native Common-backed writes to a private Redis socket. Those boundaries are precise: runfiles dependencies are borrowed, the entry loop is mocked, and LLDP command acquisition is supplied as the original JSON fixture. This is not complete image/dependency or live `lldpd` qualification.

The most useful new nonblocking correction is to stop describing Maintainer omission as a limitation of the selected wheel rule. The SONiC-patched API already exposes those fields. The outer timeout path also needs more explicit Redis-child ownership if the test is expected to clean up without relying on Bazel/container teardown.

## Source and installed-consumer assessment

### Owner payload, version and entrypoint

[Wheel/runtime producer](https://github.com/sonic-net/sonic-dbsyncd/blob/8a7eb9f3da4ea3e350c35dcc25635ee4c0b0a413/BUILD.bazel#L1-L99) · [LLDP source library](https://github.com/sonic-net/sonic-dbsyncd/blob/8a7eb9f3da4ea3e350c35dcc25635ee4c0b0a413/src/lldp_syncd/BUILD.bazel#L1-L24) · [legacy setup contract](https://github.com/sonic-net/sonic-dbsyncd/blob/8a7eb9f3da4ea3e350c35dcc25635ee4c0b0a413/setup.py#L1-L44).

The wheel contains the existing `lldp_syncd` and `sonic_syncd` package files, including `lldp_syncd/__main__.py`; the library target excludes that side-effecting CLI module. `sonic-d` remains distribution version 2.0.0. Bazel module version 2.0.1 is a different version domain and is not a demonstrated wheel-version defect.

Actual daemon, parsing, synchronization, thread and entrypoint source bytes are unchanged from BASE. The review traced them rather than assuming unchanged means irrelevant. Existing parser/frequency/thread limitations were not promoted into blockers for adding another packaging path.

### Installed wheel and declared dependency boundary

[Installed-wheel consumer](https://github.com/sonic-net/sonic-dbsyncd/blob/8a7eb9f3da4ea3e350c35dcc25635ee4c0b0a413/tests/bazel/installed_wheel_probe.py#L1-L135) compares source, wheel and installed bytes and validates runtime TAR modes/ownership/timestamps. It verifies owner and `sonic-py-common` imports resolve inside the private site. The exact buildimage fixture installs those two wheels and uses a `.pth` file to borrow other declared runfiles dependencies, excluding owner source roots.

That fixture is not independent installation of every dependency, and the README explicitly says so. The runtime TAR is an owner-only layer, not a standalone daemon image. The production source library declares the native Common binding; the application supplies other runtime owners.

The entry test runs `python -m lldp_syncd` with `-d 10`, mocks only `lldp_syncd.main.main`, and expects `update_frequency=None`. The real options helper assigns `-d` to logging, while `-f` assigns frequency; the assertion matches the actual caller semantics.

### Native LLDP writes and lifecycle

[Native Redis probe](https://github.com/sonic-net/sonic-dbsyncd/blob/8a7eb9f3da4ea3e350c35dcc25635ee4c0b0a413/tests/bazel/native_redis_probe.py#L19-L96) uses `--port 0`, a private Unix socket and temporary DB configuration, checks empty state/PID ownership, and constructs the real `SonicV2Connector`. It calls the unchanged `parse_update`/`sync` path with the original LLDP JSON fixture.

Deep copies are taken before `sync` removes local-chassis data or retains neighbor dictionaries as cache. Assertions cover initial neighbor/chassis hashes, one description update, and deletion of neighbors while preserving local chassis. Normal completion and ordinary Python exceptions terminate/wait/kill Redis. No native probe was executed by this review.

The probe does not run the actual acquisition commands, thread loop or Docker daemon. Its receipt wording that the daemon “is tested by Docker integration” is broader than evidence produced here; a safer description is “real daemon/lldpctl execution not exercised by this probe.” This is an evidence-scope clarification, not a separate runtime blocker.

## Nonblocking findings

### N1 — Preserve metadata that the selected wheel API already supports

[Wheel declaration](https://github.com/sonic-net/sonic-dbsyncd/blob/8a7eb9f3da4ea3e350c35dcc25635ee4c0b0a413/BUILD.bazel#L28-L45) · [absence assertion/receipt](https://github.com/sonic-net/sonic-dbsyncd/blob/8a7eb9f3da4ea3e350c35dcc25635ee4c0b0a413/tests/bazel/installed_wheel_probe.py#L35-L69) · [README explanation](https://github.com/sonic-net/sonic-dbsyncd/blob/8a7eb9f3da4ea3e350c35dcc25635ee4c0b0a413/README.md#L54-L57) · [selected registry patch](https://github.com/sonic-net/sonic-bazel-registry/blob/5bc060679a7a09d6a9b7885a746d282abe34c064/modules/rules_python/1.9.0.sonic.2/patches/0003-preserve-wheel-metadata-and-modes.patch).

Both workspaces select `rules_python 1.9.0.sonic.2`. Its actual patch adds `maintainer` and `maintainer_email`, emits the corresponding METADATA fields and tests them in a registry consumer. The new owner wheel passes neither attribute, while its test requires their absence and says they are unsupported.

Thus the new path unnecessarily loses contact metadata present in `setup.py`; the claimed tool limitation is false for the selected release. This is nonblocking package fidelity/documentation, not daemon behavior.

**Correction:** pass the existing setup-contract fields into the wheel rule, compare them in `test_complete_owner_payload_and_metadata`, and remove the unsupported-fields exception/README rationale. If omission is deliberately retained, state that policy choice instead of claiming incapability. The patch also supports `regular_file_mode="0644"`; using it to simplify repackaging is optional and needs its own retained TAR checks.

### N2 — Own private Redis cleanup across the outer probe timeout

[Outer child timeout](https://github.com/sonic-net/sonic-dbsyncd/blob/8a7eb9f3da4ea3e350c35dcc25635ee4c0b0a413/tests/bazel/installed_wheel_probe.py#L120-L126) · [Redis child creation and cleanup](https://github.com/sonic-net/sonic-dbsyncd/blob/8a7eb9f3da4ea3e350c35dcc25635ee4c0b0a413/tests/bazel/native_redis_probe.py#L38-L92).

If the native probe stalls after starting Redis, the outer `subprocess.run(... timeout=60)` kills the direct probe process. Redis cleanup lives in that process's Python `finally`, which cannot run after the timeout kill. No surviving-parent ownership or process-group cleanup is declared.

Bazel/container teardown may contain the remaining process, but the probe itself does not guarantee cleanup on this path. This is conditional test robustness; no timeout or production failure was reproduced.

**Correction:** keep Redis ownership in a surviving parent, or use a dedicated process group/session and bounded group cleanup on timeout. Retain the private socket and ordinary terminate/wait/kill controls; this can follow separately.
