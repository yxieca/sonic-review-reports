## Detailed findings and retained mismatch evidence

### R1 — Reconcile the default APT resolver with the new registry (P2 blocker; awaiting author)

[Changed default registry](https://github.com/sonic-net/sonic-build-infra/blob/57f537b9ec9cedc797a19ffade867b3b285a3a9f/apt/lock.py#L548-L593), [resolver default](https://github.com/sonic-net/sonic-build-infra/blob/57f537b9ec9cedc797a19ffade867b3b285a3a9f/apt/lock.py#L21), [actual update caller](https://github.com/sonic-net/sonic-build-infra/blob/57f537b9ec9cedc797a19ffade867b3b285a3a9f/apt/README.md#L85-L110).

The documented bootstrap `apt/lock.py update` command supplies neither a registry nor a resolver-version override. `main` defaults to `rules_distroless 0.9.4.sonic.20`; `resolve` carries that option into a separately generated root MODULE. This PR changes that root's default registry from the former catalog to canonical SONiC followed by BCR.

At [canonical registry snapshot `5bc06067`](https://github.com/sonic-net/sonic-bazel-registry/blob/5bc060679a7a09d6a9b7885a746d282abe34c064/modules/rules_distroless/metadata.json), only `.26` is published. Exact `.20` lookups at that snapshot and BCR returned Not Found. The [former registry's immutable `.20` record](https://github.com/securely1g/sonic-bazel-registry/blob/78f8757b1cb9be33ffe9ce804f5ef104f3a0a47c/modules/rules_distroless/0.9.4.sonic.20/source.json) exists. Thus the endpoint change introduces an update-availability regression even though the version constant is inherited.

Normal locked imports and `check` are different paths; their green CI does not invoke this updater resolver. Failure occurs before replacing the production lock. Explicit overrides or a reviewed `--resolved-lock` can avoid it, but do not repair the documented default.

**Correction:** publish the compatible `.20` recipe at the canonical registry, or deliberately migrate the updater and recorded lock-input provenance to an available resolver. Changing the constant alone is insufficient: `_inputs` includes the resolver version and digest. Add a default-route regression without overrides masking the endpoint/version pair.

### R2 — Reject or normalize an unterminated final mtree record (P3; nonblocking)

> **Current disposition:** optional input-contract hardening, not a before-merge condition. The original severity interpretation is superseded by the dated reassessment above. Python parser acceptance does not establish intended supported production input; the technical mismatch evidence below is retained.

[New summary](https://github.com/sonic-net/sonic-build-infra/blob/57f537b9ec9cedc797a19ffade867b3b285a3a9f/deb/mtree.py#L23-L57), [direct assembly route](https://github.com/sonic-net/sonic-build-infra/blob/57f537b9ec9cedc797a19ffade867b3b285a3a9f/deb/assemble.py#L171-L181), [raw-spec archive invocation](https://github.com/sonic-net/sonic-build-infra/blob/57f537b9ec9cedc797a19ffade867b3b285a3a9f/deb/assemble.py#L207-L221).

A Python-accepted flat specification ending immediately after its final file record, without LF, passes Python's `splitlines()` summary; intended supported production use of this form was not established. Its file contributes `md5sums`, `Installed-Size` and payload-presence checks. The assembler then passes the unchanged file to the selected BSDtar reader.

The execution toolchain selects locked Debian libarchive-tools **3.7.4-4+deb13u1**, not the separately available 3.8.1 bootstrap fallback. In [3.7.4 `readline`](https://github.com/libarchive/libarchive/blob/v3.7.4/libarchive/archive_read_support_format_mtree.c#L2089-L2158), EOF returns zero even after collecting an unterminated record; [`read_mtree`](https://github.com/libarchive/libarchive/blob/v3.7.4/libarchive/archive_read_support_format_mtree.c#L1034-L1108) treats that as successful end-of-input. The final record is not emitted. Consequently, generated control metadata describes a file absent from the data archive.

This backend behavior is inherited; the new opt-in interface can independently summarize a record the backend drops. The original blocking classification is withdrawn; no supported production caller emitting this form was established. The existing tar.bzl macro [explicitly adds a final newline](https://github.com/bazel-contrib/tar.bzl/blob/8dae43618053a24039e2b4e8c3fcbab8d9b46b55/tar/tar.bzl#L138-L147), but the direct assembler route does not call it.

**Correction:** reject missing final LF, or normalize one small manifest and use the same representation for summary and production. Add a complete mtree package membership/`md5sums` regression, with LF and no-LF controls. The Python acceptance was evaluated with closed in-memory inputs; archive omission is source-derived, not a locally executed DEB reproduction.

### R3 — Enforce unambiguous flat destination names (P3; nonblocking)

> **Current disposition:** optional flat-grammar hardening, not a before-merge condition. The original severity interpretation is superseded by the dated reassessment above. No supported production caller generating these bare-name forms was established; the technical mismatch evidence below is retained.

[Path interpretation and summary](https://github.com/sonic-net/sonic-build-infra/blob/57f537b9ec9cedc797a19ffade867b3b285a3a9f/deb/mtree.py#L13-L57), [conffile lookup](https://github.com/sonic-net/sonic-build-infra/blob/57f537b9ec9cedc797a19ffade867b3b285a3a9f/deb/assemble.py#L182-L188).

Consider a specification containing root `.`, bare directory `a`, and then bare file `f` with declared `contents=inputs/payload`. Python treats `a` and `f` as independent root-relative destinations; both have `.` as parent, and `/f` passes conffile validation.

The selected reader [marks `.` or names containing `/` as full paths](https://github.com/libarchive/libarchive/blob/v3.7.4/libarchive/archive_read_support_format_mtree.c#L1942-L1953). Bare `a` is instead a relative directory that updates `current_dir`; subsequent bare `f` becomes **`a/f`** in [`parse_file`](https://github.com/libarchive/libarchive/blob/v3.7.4/libarchive/archive_read_support_format_mtree.c#L1194-L1230). The raw-spec invocation does not constrain emitted names to the Python destination map. Payload location, checksums and conffile declarations can therefore disagree.

This is source-derived mismatch evidence in the new opt-in interface, not a demonstrated supported-input regression or a regression in default TAR consumers. It does not require supporting general hierarchical mtree syntax: a restricted flat API can reject ambiguous spellings.

**Correction:** require unambiguous full-path spellings such as appropriately encoded `./…` for non-root records, or emit a canonical validated specification used by both summary and producer. Add bare-name/full-path controls through complete mtree package assembly. Python acceptance and lookup were evaluated with closed in-memory inputs; backend path behavior was inspected statically.
