## Grounded nonblocking corrections

### 1. Make E3-04 distinguish the actual CoS-to-queue mapping

Anchor: [`scaleup_esun_testplan.md:410`](https://github.com/sonic-net/sonic-mgmt/blob/a8b9d1a0191ad78a0f030ae1849cd496c826668d/docs/testplan/scaleup/scaleup_esun_testplan.md#L410), with E3-01 at407 and common rules333–366.

E3-04 sends 100 packets for each of eight CoS values in an interleaved stream. It checks 100 packets in each queue before and after changing a reversed map back to the identity map. A DUT that stays on the identity map throughout produces exactly the same queue histogram as a DUT that correctly changes maps: `[100,100,100,100,100,100,100,100]`. Staying on the reversed map also passes those totals. Physical-port reception and unchanged EH-CoS do not reveal which queue each packet used.

Coordinator controls evaluated all **40,320 bijective mappings**; every mapping satisfies the stated aggregate totals. A correct reversed-map control passes, an all-to-one-queue fault is rejected, and eight one-CoS-at-a-time controls distinguish the ignored-remap fault. These are arithmetic checks of the document's observables, **not 40,320 product tests**.

**Suggested correction:** repeat E3-01's per-CoS counter-delta measurements under both maps, or send unequal counts for each CoS so each expected queue total identifies its source class. Explicitly drain/reset or snapshot between phases. Preserve the useful no-restart remap scenario.

Counterargument retained: the Expected Result could imply additional per-CoS attribution that the author plans to implement. If so, state that observation explicitly; ordinary PTF capture on one physical egress port does not itself provide queue identity. E3-01's identity-only check does not establish the reversed mapping or transition.

### 2. Clarify per-subrun counter windows and queue prerequisites

Anchors:340,380,407–410,448–449.

BASE clears counters at case start; E3-01 also clears per CoS, but E3-02/03 swap target/competing queues and E3-04 repeats a batch without saying whether assertions use fresh deltas. Correct classification can leave100 packets in the previous target queue when the next run requires it to count0. The coordinator's cumulative-versus-delta control confirms that explicit per-subrun deltas resolve this. Readers may already intend deltas, so this is a wording clarification, not a proven future failure.

E1-05 also needs CoS0/3/7 mapped to distinct queues, and E6-02 needs CoS3's profiled queue distinct from CoS4's control queue. BASE does not specify the default map. Reuse the explicit map or declare/verify these preconditions; no vendor-default mismatch has been established.

### 3. State where E5-01's hop count starts

Anchor:435.

The frame captured after input TTL15 already has TTL14. Reinjecting that captured frame yields13 further forwards, then drops on reinjection14. Starting instead from the original TTL15 frame yields14 forwards and a drop on injection15. Both paths were checked offline.

The existing counts are coherent if they include the original transmission. Say that explicitly, or begin step3 with a fresh TTL15 frame. This is an off-by-one interpretation risk, not a normative TTL defect; E5-02 separately covers TTL0/1 drop and TTL2 success.

### 4. Define repetition for the sparse Flow Label run

Anchor:425.

With a fixed lower byte and only the upper byte varying, there are256 distinct16-bit labels, not10,000. The sparse run can send10,000 packets by repeating labels, but cannot retain the random run's uniqueness requirement. Clarify that repetition is allowed and define its weighting. If “without repetition” was intended only for the first random run, this is simply making that scope explicit.
