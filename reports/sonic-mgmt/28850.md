## R1 — Failed API cleanup must not finish as successful teardown

**Kind:** Blocking. **Severity:** P2. **Disposition:** Open.

**Anchors:** [thermal leak fixture](https://github.com/sonic-net/sonic-mgmt/blob/834b687c739eb0b5e72ad49770afc8a9a9cd6a30/tests/platform_tests/api/test_thermal_leak_sensor.py#L147-L160), [liquid cooling fixture](https://github.com/sonic-net/sonic-mgmt/blob/834b687c739eb0b5e72ad49770afc8a9a9cd6a30/tests/platform_tests/api/test_liquid_cooling_leakage.py#L89-L103).

The API contract returns `False` when test leaks remain. Both newly added injection-fixture finalizers only log a warning and return normally when cleanup is not confirmed. The inspected platform implementation can return false on marker-withdrawal failure. A simulated leak can therefore contaminate subsequent tests without unsuccessful teardown.

**Evidence:** An exact-source inert fixture control returned normally with a warning when its fake bulk-clear operation returned false. This is a documented failure-path counterexample, not a claim that every test leaves a leak or that a live device did so.

**Introduced or inherited:** A gap in the new API injection/cleanup path, not a pre-existing master fixture.

**Smallest requested correction:** Fail teardown when cleanup cannot be confirmed. Per-sensor fallback/refactoring can be handled separately; no new framework is required.

**Discussion:** [Existing request](https://github.com/sonic-net/sonic-mgmt/pull/28850#discussion_r4635984489). The author explicitly chose warning-only handling to keep the tests simple. That is an answer, not an ignored request; UI resolution does not establish restored state. Reference the existing discussion rather than post it again as a newly discovered issue.

## R2 — Observe probe recovery before beginning a new marker-scoped episode

**Kind:** Conditional blocking. **Severity:** P2. **Disposition:** Open; follow-up candidate, not accepted deferral.

**Anchors:** [capability probe helper](https://github.com/sonic-net/sonic-mgmt/blob/834b687c739eb0b5e72ad49770afc8a9a9cd6a30/tests/common/helpers/platform_api/leak_sensor_test.py#L78-L110), [injector recovery wait](https://github.com/sonic-net/sonic-mgmt/blob/834b687c739eb0b5e72ad49770afc8a9a9cd6a30/tests/common/helpers/bmc_liquid_leakage_control_test_helper.py#L201-L215).

Capability probing briefly injects and withdraws severities. The subsequent wait can accept the original stale `leaking=No` row before the daemon publishes the probe. If reinjection happens before a clear poll, the daemon can retain the same episode and emit no new onset inside the test's log marker. Waiting after reinjection cannot recreate that missing transition. A recovery timeout also only warns and continues.

**Evidence:** The inspected daemon state-machine body was executed with fake sensor/database/log state in a deterministic read-before-publication interleaving. The current predicate accepted old No, and reinjection produced no fresh onset. A clear-poll control produced the expected event. No real thread, daemon or device was run.

**Introduced or inherited:** Existing asynchronous polling exposed by the newly added probing/reuse sequence.

**Requested correction or deferral condition:** Establish observation/withdrawal/recovery ordering or demonstrate an equivalent fresh-episode guarantee. A separate follow-up may be reasonable if an explicit, supported containment prevents an uncertain-recovery scenario from running. A narrow-window assertion alone is not verified containment.

**Discussion:** [Existing request and response](https://github.com/sonic-net/sonic-mgmt/pull/28850#discussion_r4635984494). The author acknowledges the stale window and considers extra waits unnecessary. This review disagrees on the specific interleaving; it does not allege physical damage.

## R3 — Recover vendor power-down after MINOR-to-MAJOR escalation

**Kind:** Blocking. **Severity:** P2. **Disposition:** Open.

**Anchor:** [aggregation cleanup guard](https://github.com/sonic-net/sonic-mgmt/blob/834b687c739eb0b5e72ad49770afc8a9a9cd6a30/tests/platform_tests/daemon/test_thermalctld.py#L448-L565).

The time-escalation case starts with expected MINOR and then waits for MAJOR. A vendor fallback using physical-reading simulation, combined with a MAJOR power-down policy, can remove host power. The new cleanup guard checks the initial expected CRITICAL/MAJOR value, so it omits recovery for this escalation case.

**Evidence:** The exact base caller records recovery, while the current guard records none for MINOR + escalation + MAJOR power-down. Direct MAJOR and CRITICAL controls recover. The inspected vendor fallback restores sensor links/scripts but does not repower the host; the daemon likewise does not repower on clear.

**Introduced or inherited:** Direct regression: the base aggregation cleanup recovered unconditionally; this PR narrows the guard and misses an existing escalation case.

**Scope:** Conditional on an eligible vendor fallback/sensor profile and a configured MAJOR removal action. This is not a universal Nexthop/API shutdown claim or an observed stranded live host.

**Smallest requested correction:** Include severities actually reached by vendor cases, including escalation, while preserving the exclusion for non-mitigating API test leaks.

**Discussion:** [Existing unresolved thread](https://github.com/sonic-net/sonic-mgmt/pull/28850#discussion_r4644242759). Avoid duplicate posting; use this thread or reference it in consolidated feedback.
