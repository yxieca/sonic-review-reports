## Summary

The PR adds six Event Handling test functions across four modules: reset, ordinary low-power mode, boot-up low-power mode, Tx disable, frequency tuning and Tx-power tuning. It also adds shared CMIS, CLI, log and restoration helpers.

Much of the earlier review has been addressed: in-process pmon backup survives reboot, HWSKU precedence is correct, selected-port dictionaries are used, timing units are milliseconds, Tx measurement is module-local on the DUT, affected CMIS-only paths are filtered, recovery uses safer finally ordering, and C-CMIS checks applied STATE_DB values rather than CONFIG_DB alone.

**The rebase is present, but argument wiring is still broken against the helper definitions already in this head.** We also identified a distinct new safety defect: a failed read of an existing pmon configuration can cause cleanup to delete that unbacked-up file. The existing Tx-oracle and syslog-observation concerns remain valid after independent inert controls.

## Blocking issues

### 1. P2 — supply the mandatory recovery and CMIS arguments

**Existing human concern, independently confirmed; do not repost as new.**

The actual `tests/transceiver/common/verification.py` requires:
- `standard_port_recovery_and_verification(..., *, port_peers, ...)` at lines456–463.
- `check_cmis_state(..., *, port_attributes_dict, timeout_sec, ...)` at lines325–328.

The five recovery call sites omit `port_peers`:
- `test_ccmis_tuning.py:271–277` — shared by both tuning tests, including default restoration.
- `test_low_power_mode.py:143–149,246–252`.
- `test_transceiver_reset.py:183–189`.
- `test_tx_disable.py:185–191`.

The Tx precheck at `test_tx_disable.py:96–98` also omits both mandatory CMIS keywords. All paths are under `tests/transceiver/system/event_handling/`.

Coordinator execution of Python's actual argument binder rejects all six call sites; adding the required keywords makes all six controls bind. The Tx precheck fails before disabling Tx. The other tests can already have performed their disruptive operation before reaching their bad recovery call—this is **not** a safe pre-device failure for every test.

**Required correction:** request the existing `port_peers` fixture in the public tests and pass it through the tuning helpers; supply the documented attributes and DOM recovery timeout to `check_cmis_state`. Do not weaken the shared verifier. Another rebase alone is not sufficient: #28393's required signatures are already present in the reviewed archive.

### 2. P2 — do not delete an existing pmon configuration when its backup read fails

**Newly identified failure path, distinct from the corrected reboot-backup problem.**

`common/state_management.py:167–173` confirms that `pmon_daemon_control.json` exists, then returns `(None, error)` if `cat` fails. The setup-error branch in `test_low_power_mode.py:198–203` always calls `restore_pmon_daemon_control` with that result. The restorer at `state_management.py:241–260` interprets `None` as “originally absent” and removes the file.

An existing configuration can therefore be deleted after a transient/read-permission failure, even though setup never modified it and never captured its original contents. The test then raises an ordinary failure with no backup available to recover the deleted platform/HWSKU file. The later per-session port restorer cannot reconstruct those contents.

**Independent control:** the exact setup helper, restore helper and boot-test error branch ran against an in-memory fake host. The recorded sequence was read failure → removal, with no prior copy. Successful existing-file and genuinely-absent-file controls both restored correctly.

**Required correction:** distinguish backup unavailable from originally absent, and do not invoke destructive restoration when backup acquisition failed before mutation. Preserve the controller-resident backup and successful absent-file cleanup; returning the selected path and a valid restoration token would make ownership explicit.

### 3. P2 — Tx-disable success must prove complete valid lane departure within a defensible observation interval

**Existing human concern, independently reproduced.**

`common/cli_helpers.py:455–486` treats `get_datapath_state() or {}` as a state map and uses `any(states.get(k) != 'DataPathActivated' ...)`. The caller at `test_tx_disable.py:140–164` accepts the returned time without checking a complete final lane set.

Running the exact generated snippet with inert platform/time objects showed:
- All eight lanes leaving: accepted, as expected.
- All eight still activated: rejected, as expected.
- One lane leaving while seven remain activated: accepted incorrectly.
- A `None` response or incomplete state map after disable: accepted incorrectly.

The timer also records the **start** of the successful read, not an established transition-completion instant. A deterministic model with a 2ms transition and 3ms state read passed a 1ms budget, reporting about0.1ms. This is an observation-boundary defect, not evidence of a real module's timing.

**Required correction:** separate valid complete data from unknown/missing data, require the intended module-wide departure, and retain observation bounds/uncertainty when comparing against short budgets. Preserve the improved per-module on-DUT measurement. Do not restore host-roundtrip timing or merely replace the shared precheck predicate without considering its all-active initial contract.

The current argument mismatch prevents ordinary reach of this path; these are isolated controls of the new oracle that must be correct once argument wiring is repaired.

### 4. P2 — the OIR absence check can report clean without observing the required log window

**Existing rotation concern confirmed; additional scan-error and window-end limitations retained.**

`common/syslog_helpers.py:17–48` remembers only a line count and later tails only the current `/var/log/syslog`. The sole reset caller captures the cursor at `test_transceiver_reset.py:114` and scans at `:124`, before shutdown/startup and final recovery.

Coordinator-run real `tail`/`grep` controls, redirected exclusively to artifact fixtures, found:
- A selected-port event is detected without rotation.
- After replacing the log with a shorter file containing that event, the old cursor returns no matches and no error.
- If the source log cannot be read, the pipeline can still return grep's no-match status, which the wrapper accepts as a clean scan.

The source ordering also ends observation before the reset→recovery window specified in `system_test_plan.md:276` has completed.

**Required correction:** use the plan's rotation-aware LogAnalyzer window, or an equivalent cursor with explicit read-error handling and complete window coverage. Close the assertion after recovery while retaining unconditional cleanup. A missing observation must not become evidence of no OIR.

## Grounded nonblocking notes

- **OIR attribution:** the generic regex also matches unrelated ports. Exact grep controls confirm this, and pinned xcvrd source prefixes the logical port at its event logging sites. Restrict the result to the selected ports and correct the inaccurate portless-log comment. This already has a human thread.
- **Low-power abort classification:** the bulk setter combines command errors with readback errors; the test exits the session even if the final read shows `Off`. Inert controls confirm the conflation. Retain command errors as test failures, but distinguish safely restored, still-On and unknown state before choosing a session-wide safety stop. The particular passive-DAC example was not independently exercised on hardware.
- **Lane positions:** summing `host_lane_count` and checking lanes1..N loses explicit mask positions. The actual parser accepts both0x0F and0xF0 with count4, while the new aggregator selects1..4 for either. No deployed sparse/high-lane fixture was established, so this is a conditional support note, not a claim that ordinary complete breakout groups all fail. Using the union of resolved host masks would match the current shared verifier.
- **Boot precondition:** check directly that xcvrd is stopped before interpreting boot-up LPMode. The existing guard is an indirect critical-list/template check. Current pinned buildimage has an empty critical-process file; this is source evidence, not proof of the author's deployed image or an executed template/boot result.
- **Scope/documentation:** record Event Handling TC5 randomized concurrent breakout recovery as a follow-up if intentionally excluded; ordinary bulk reset is not that stress scenario. The new syslog helper/category fixture are missing from the organization diagram.
