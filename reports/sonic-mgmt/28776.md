## Summary

The four added lines correctly avoid an IxNetwork-only CRC lookup when the API lacks `_ixnetwork`. They preserve the existing CRC failure path for a backend exposing that client. The checker returns, not the entire pytest test: downstream flow, loss and DUT assertions remain intact.

**Do not describe this as complete GrpcApi support for `run_traffic()`.** Its earlier `_log_in_flight_stats()` still dereferences `_ixnetwork` and fails before reaching this guard. That problem is unchanged from base. The separate non-IMIX `run_traffic_and_collect_stats()` path benefits from this narrow correction.

## Grounded nonblocking note

**N1 — Narrow the claimed `run_traffic()` compatibility.**

At `tests/common/snappi_tests/traffic_generation.py:734–742`, `_log_in_flight_stats()` uses `api._ixnetwork` for ordinary non-MACsec traffic. Both `run_traffic()` polling branches call it at `920–934`, before the patched CRC call at `1008`. The actual PFC caller is `tests/snappi_tests/pfc/files/helper.py:268–275`.

The exact logger body raises `AttributeError` with an absent-client API on **both base and head** in coordinator-owned inert evaluation. Please describe this patch as fixing the CRC helper/non-IMIX collector, explicitly noting the remaining logger problem, or address that logger separately while retaining generic flow statistics. This does not require withholding the useful CRC fix.

## Optional suggestion, not a required nit

A debug/info message before the new return (`640–643`) could distinguish “CRC unavailable for this backend” from “CRC checked clean.” No existing caller requires such a status, so this is observability advice only.
