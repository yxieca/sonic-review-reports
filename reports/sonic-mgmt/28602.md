## Summary

The PR adds five files / 793 lines implementing a physical-DUT SATA/NVMe health baseline, sequential-write stress, mixed-I/O stress with iostat, per-model thresholds, fixtures and a test plan. Its file-backed workload, free-space reserve, media-counter deltas and successful-path cleanup are sensible. Three blocking defects remain: the BGP snapshot misses namespaces changed by the installation helpers; originally-disabled peers are restored only after an incompatible convergence check; and post-load validation can accept loss of previously available critical health telemetry.

These are new SSD-test call-path/oracle defects, not requests to fix unrelated shared-helper behavior. The existing eBGP setup-failure recovery from #28351 is present and credited.

## Blocking issues

### B1 — P2: Restore the same per-ASIC BGP state that installation changes

**Anchor:** [`tests/platform_tests/ssd/conftest.py:103–106,123–128`](https://github.com/sonic-net/sonic-mgmt/blob/aaeafc9879ea14deb0ca747180c02382f736bc02/tests/platform_tests/ssd/conftest.py#L103).

The new fixture snapshots `config_facts(..., source="running")` without a namespace and later uses unqualified CONFIG_DB restoration. The reached `config bgp shutdown all` / `startup all` commands iterate frontend namespaces on multi-ASIC devices. The host facts wrapper does **not** implicitly collect those namespaces: without `asic_index`, it delegates to the host-global namespace.

An `asic0` neighbor originally down, or one originally lacking `admin_status`, is therefore absent from the saved host table. After installation, the all-up helper changes both to explicit `up`, and the new restoration loops have no record of them. The module is advertised for any physical topology and does not exclude multi-ASIC DUTs.

**Grounding:** coordinator executed the exact new caller and BGP helper bodies plus the pinned SONiC CLI all/leaf functions against an in-memory namespace database. With an empty host table, `asic0` neighbor A changed from down to up and neighbor B from absent status to up. The all-explicit-up control remained unchanged. Relevant external CLI source is pinned at sonic-utilities `a3619448ded40935c120f251b6dfd7be97cf6145`; this is source-contract validation, not a claim about an inspected installed image.

**Fix direction:** capture and restore presence/value by namespace and neighbor for the exact mutation domain, or explicitly constrain supported scope until that is safe. The outer module CONFIG_DB check may later detect and reload changed configuration; that does not prevent unintended peer activation during the module. No permanent outage is claimed.

### B2 — P2: Restore disabled peers before checking the original route totals

**Anchor:** [`conftest.py:121–128`](https://github.com/sonic-net/sonic-mgmt/blob/aaeafc9879ea14deb0ca747180c02382f736bc02/tests/platform_tests/ssd/conftest.py#L121).

Even on single-ASIC devices, `duthost_startup_ebgp` starts **all** peers and synchronously waits for the saved route totals. Only after it returns or fails does the fixture re-disable peers that were originally down.

If an originally-disabled peer becomes reachable and advertises at least five additional distinct routes, the helper cannot reach the old route total while that peer remains enabled. Successful tool installation then fails setup after the readiness wait. The `finally` does eventually restore the single-ASIC peer state; the defect is the ordering and false setup failure, not complete absence of cleanup.

**Grounding:** actual caller, startup/shutdown helpers, route-count predicate and retry evaluator ran with a virtual clock and fake command endpoints. Baseline10 routes became110 after all-up; setup failed before the recorded per-peer shutdown. All-initially-up control passed.

**Fix direction:** separate activation/restoration from readiness: restore exactly the original state first, then validate convergence against the original route counts. Include the helper's own failure-path recovery in the design.

### B3 — P2: Reject disappearance of previously available critical health data after stress

**Anchor:** [`test_ssd_health.py:216–232`](https://github.com/sonic-net/sonic-mgmt/blob/aaeafc9879ea14deb0ca747180c02382f736bc02/tests/platform_tests/ssd/test_ssd_health.py#L216); callers at332 and359.

The delta validator checks post-load SMART/warning/temperature through a helper that ignores missing values. It detects disappearance only for media-error counters. Thus a temperature or overall-health field known before stress can disappear afterwards without failing the test.

The strongest case is an eligible SATA baseline with real SMART/temperature/wear readings but unsupported vendor media counters. If the after collection becomes entirely unreadable, the delta still passes: critical checks see None and the media loop skips counters absent before. The baseline validator would skip that same unreadable snapshot, but neither stress test invokes its all-missing guard after the load.

**Grounding:** actual validators accepted both partial critical-field loss with unchanged media counters and complete post-load loss for a valid no-media-counter baseline. Healthy controls passed; overtemperature and increased-media-counter controls failed as intended.

**Fix direction:** retain which critical fields were available before stress and fail explicitly when those measurements disappear; at minimum reject an entirely unreadable after snapshot. Continue tolerating genuinely unsupported fields absent from the start. Distinguish query/parse failures from unsupported telemetry rather than silently treating both as missing fields.

## Grounded nonblocking notes

1. **Async iostat cleanup:** `test_ssd_health.py:261–267` closes/joins the controller pool only after successful fio and result retrieval. An inert fio-error control skipped both operations; the success control closed/joined. Add exception-safe ownership while preserving the original fio error. Downgraded from some reviewers' blocking severity: sampling is finite, and no permanent leak or cross-test failure was demonstrated.
2. **Package rollback is narrower than “left as found”:** `conftest.py:115–120,138–146` records only successful top-level installs. A simulated post-unpack install failure skips before recording the attempted package, leaving it outside cleanup; successful fixture cleanup passed. Dependencies/upgrades, ignored purge failures and unbounded purge also limit the restoration promise. This is not a real package-transaction reproduction or evidence of a damaged DUT; treat as a qualified robustness follow-up, not an automatic blocker. Avoid indiscriminate autoremove.
3. **Post-load wear threshold:** wear90→91 with maximum90 passes the delta although the same after snapshot fails baseline validation. The detailed stress plan explicitly promises temperature and media-delta checks, so this is a nonblocking contract-consistency question rather than an invented mandatory endurance oracle: should post-load wear also meet the configured limit?
4. **Document qualification precisely:** unknown SATA/NVMe models deliberately fail the threshold fixture, unlike unsupported transports/tools that skip. State that onboarding policy explicitly. The overview's “trend across runs” overstates the current per-load counter comparison; no historical trend is persisted. The utility setup list should also include iostat/sysstat.
5. **NVMe timeout-log coverage:** the actual regex misses the Linux6.12 `I/O tag ... timeout, aborting req_op...` format while catching older numeric-I/O timeout and controller-down controls. The format was confirmed in pinned upstream kernel source. Since the deployed kernel was not inspected, retain this as a qualified coverage question rather than asserting a fleet-wide failure.

### Important dropped/downgraded claims

- Unknown-model hard failure is explicit policy, not automatically a bug requiring skip.
- No supported listed SATA model/image was shown to lack `show platform ssdhealth`; existing exact-head CLI tests use it. Do not reflexively suppress command failures.
- The claimed iostat “zero timeout slack” is incorrect: `.get(timeout=...)` starts **after** synchronous fio returns. An actual fake-time control verified the additional wait budget.
- Zero-valued wear/media checks accept healthy values as intended. Pinned nvme-cli1.16/2.4 output supports integer Kelvin/`percent_used`; no unsupported Celsius/string bug is asserted.
- Log-only CRC/error-count fields, nonzero-throughput sanity, and iostat debug logging match the detailed plan. No arbitrary performance thresholds added.
- Empty-PKNAME layouts, missing libaio/old sysstat, other-SATA attribution, Ansible duration limits and loganalyzer concerns lack demonstrated supported-image failures. No speculative blockers retained.
