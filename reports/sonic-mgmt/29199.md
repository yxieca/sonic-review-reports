## N5 — row deletion does not cancel the bridge's in-flight command

**Condition:** the new unknown-host test publishes its POWER_ON row while bmcctld is stopped, then fails before calling the yielded restart function—for example, while asserting no premature events.

The whole [bmcctld_stopped fixture](https://github.com/sonic-net/sonic-mgmt/blob/9c2f70eeb39eb9320d9c08202e0ecb660df1ef84/tests/redfish/test_redfish_event_subscription.py#L647-L675) correctly deletes new command rows before starting bmcctld. But it does not restart/cancel sonic-dbus-bridge, which still owns that row as its pending command.

**Actual dependency caller chain:** the inspected [StateManager](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/state_manager.cpp#L247-L345) keeps `actionInProgress_` and `pendingCommandId_` after publication. Further accepted resets enter its queue and do not dispatch while the slot is busy. [Command completion](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/state_manager.cpp#L380-L438) releases the slot only for the matching terminal command status or timeout. The timeout is600seconds. The [UpdateEngine missing-row branch](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/update_engine.cpp#L197-L212) returns when the row has been deleted; republishing HOST_STATE is not command completion.

**Conditional consequence:** the bridge can retain its slot despite a restored daemon/On row, delaying a request before the next restart. However, each unknown-host parametrization restarts the bridge before its reset, these tests are at the end of their class/module, the reset-recovery case is also at its module end, and module TLS teardown recreates the Redfish container. The leak-sensor finalizer can also restart the bridge. Thus retained state is source-proven, but a normal next-test stall is not. The previous stronger blocking characterization is withdrawn; lifecycle-aware cancellation is a nonblocking reliability improvement.

**Base and counterevidence:** this fixture and unknown-host command cancellation are new; BASE has no corresponding held-command teardown. The original orphan-command issue is genuinely fixed for the pre-restart failure: the row is removed before bmcctld can execute it. This finding is the additional in-memory state left behind by that fix, not a repetition of the old unsafe-row accusation. A normal completed command, a verified bridge restart, or the timeout eventually releases the slot. Later event/fixture restarts can also recover it, but the new fixture does not guarantee that before later tests. The adjacent `bmcctld_held` fixture already restarts the bridge before deleting abandoned rows and restarting the consumer.

**Validation:** coordinator-only execution of the **exact Python fixture** with fake service/Redis calls and a clearly labeled source-derived bridge-state model leaves the deleted command in flight and the next command queued. Restart and terminal-completion controls permit the next command. The C++ bridge was not compiled or executed; the model's retention rules were independently traced through the full actual source above. No BMC, Redis, service, endpoint or process action occurred.

**Smallest correction:** while bmcctld remains stopped, cancel abandoned in-memory bridge work through a verified bridge restart or supported cancellation mechanism, then remove all test-owned command rows, restore bmcctld and verify process/recognized host readiness. Keep those cleanup steps reliable on failure; do not restart the consumer while an abandoned command remains executable. Add an early-failure teardown case followed by a new reset that demonstrates command dispatch without waiting for the old timeout.

## Existing nonblocking suggestions

### N1 — daemon readiness must not be inferred from a synthetic row

The fixture's `_start()` waits for any truthy HOST_STATE hash. The `unrecognised` parametrization writes such a row itself; the original On row can also remain after an earlier failure. SonicHost's start helper ignores command errors and does not itself establish readiness. The body later checks settled On and positive GET state, so this is not a false-green whole test; fixture restoration verification can still be misleading.

The current human review explicitly classified this suggestion as nonblocking. Retain a targeted improvement: wait for `bmcctld_running` and then recognized/repopulated host state separately. Do not turn it into a new hardware-outage assertion. N5 above concerns the distinct bridge action-slot ownership, which a running bmcctld check would not cure.

### N2 — asynchronous command publication and later cleanup

Recovery after bridge-down returns on HTTP204 and then performs an immediate key-delta cleanup. The bridge publishes through an asynchronous timer, so that scan can precede its row. The unknown-host fixture's cleanup is also gated on bmcctld still being stopped; failures after the body restarts it skip the body-end cleanup.

These POWER_ON requests have an already-On precondition and the suite also intentionally retains completed command history. Current human review treats them as nonblocking cleanup reliability issues. Coordinate publication/completion or cancellation with a final cleanup; do not claim observed destructive power changes.

### N3 — distinguish what the assertions actually prove

The ResourceEvent registry includes leak status events as well as host power events, so exact registry-wide event equality is stronger than an ordered host-power subsequence. Existing isolation limits the risk, and the BASE test already rejects unrelated leak delivery through another subscriber; no independently demonstrated new blocker is retained.

Bridge-down tests intentionally permit401/500 auth-path failures as well as503. Retry-After is validated **only when503 occurs**, not on every green run. Explicitly record when that branch was not exercised if reporting header coverage. The helper now uses ASCII delay digits and returns the original string consistently; inert cases reject superscript/Arabic digits with AssertionError instead of leaking ValueError.

A prior suggestion to filter every liquid-cooling row by `type == leak` is **not adopted**: the actual Redfish41 Redis adapter exports all nonempty `LIQUID_COOLING_INFO|*` rows and treats `type` as sensor information, not that selection predicate. The new collection comparison matches the inspected dependency. A proposed filter must follow the real producer contract rather than the synthetic fixture's chosen type.
