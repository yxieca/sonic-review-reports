## N5 — row deletion does not cancel the bridge's in-flight command

**Condition:** the new unknown-host test publishes its POWER_ON row while bmcctld is stopped, then fails before calling the yielded restart function—for example, while asserting no premature events.

The whole [bmcctld_stopped fixture](https://github.com/sonic-net/sonic-mgmt/blob/9c2f70eeb39eb9320d9c08202e0ecb660df1ef84/tests/redfish/test_redfish_event_subscription.py#L647-L675) correctly deletes new command rows before starting bmcctld. But it does not restart/cancel sonic-dbus-bridge, which still owns that row as its pending command.

**Actual dependency caller chain:** the inspected [StateManager](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/state_manager.cpp#L247-L345) keeps `actionInProgress_` and `pendingCommandId_` after publication. Further accepted resets enter its queue and do not dispatch while the slot is busy. [Command completion](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/state_manager.cpp#L380-L438) releases the slot only for the matching terminal command status or timeout. The timeout is600seconds. The [UpdateEngine missing-row branch](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/update_engine.cpp#L197-L212) returns when the row has been deleted; republishing HOST_STATE is not command completion.

**Conditional consequence:** the bridge can retain its slot despite a restored daemon/On row, delaying a request before the next restart. However, each unknown-host parametrization restarts the bridge before its reset, these tests are at the end of their class/module, the reset-recovery case is also at its module end, and module TLS teardown recreates the Redfish container. The leak-sensor finalizer can also restart the bridge. Thus retained state is source-proven, but a normal next-test stall is not. The previous stronger blocking characterization is withdrawn; lifecycle-aware cancellation is a nonblocking reliability improvement.

**Base and counterevidence:** this fixture and unknown-host command cancellation are new; BASE has no corresponding held-command teardown. The original orphan-command issue is genuinely fixed for the pre-restart failure: the row is removed before bmcctld can execute it. A normal completed command, a verified bridge restart, or the timeout eventually releases the slot. ## N5 — row deletion does not cancel the bridge's in-flight command

**Condition:** the new unknown-host test publishes its POWER_ON row while bmcctld is stopped, then fails before calling the yielded restart function—for example, while asserting no premature events.

The whole [bmcctld_stopped fixture](https://github.com/sonic-net/sonic-mgmt/blob/9c2f70eeb39eb9320d9c08202e0ecb660df1ef84/tests/redfish/test_redfish_event_subscription.py#L647-L675) correctly deletes new command rows before starting bmcctld. But it does not restart/cancel sonic-dbus-bridge, which still owns that row as its pending command.

**Actual dependency caller chain:** the inspected [StateManager](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/state_manager.cpp#L247-L345) keeps `actionInProgress_` and `pendingCommandId_` after publication. Further accepted resets enter its queue and do not dispatch while the slot is busy. [Command completion](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/state_manager.cpp#L380-L438) releases the slot only for the matching terminal command status or timeout. The timeout is600seconds. The [UpdateEngine missing-row branch](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/update_engine.cpp#L197-L212) returns when the row has been deleted; republishing HOST_STATE is not command completion.

**Conditional consequence:** the bridge can retain its slot despite a restored daemon/On row, delaying a request before the next restart. However, each unknown-host parametrization restarts the bridge before its reset, these tests are at the end of their class/module, the reset-recovery case is also at its module end, and module TLS teardown recreates the Redfish container. The leak-sensor finalizer can also restart the bridge. Thus retained state is source-proven, but a normal next-test stall is not. The previous stronger blocking characterization is withdrawn; lifecycle-aware cancellation is a nonblocking reliability improvement.

**Base and counterevidence:** this fixture and unknown-host command cancellation are new; BASE has no corresponding held-command teardown. The original orphan-command issue is genuinely fixed for the pre-restart failure: the row is removed before bmcctld can execute it. This finding is the additional in-memory state left behind by that fix, not a repetition of the old unsafe-row accusation. A normal completed command, a verified bridge restart, or the timeout eventually releases the slot. Later event/fixture restarts can also recover it, but the new fixture does not guarantee that before later tests. The adjacent `bmcctld_held` fixture already restarts the bridge before deleting abandoned rows and restarting the consumer.

**Validation:** coordinator-only execution of the **exact Python fixture** with fake service/Redis calls and a clearly labeled source-derived bridge-state model leaves the deleted command in flight and the next command queued. The C++ bridge was not compiled or executed; the model's retention rules were independently traced through the full actual source above. No BMC, Redis, service, endpoint or process action occurred.
