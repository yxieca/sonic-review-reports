## Summary

GNMIEnvironment previously ran `docker exec gnmi ps aux | grep telemetry` when GNMI configuration was absent. Because the container shares host PID visibility, that output can put another container's telemetry server first, yielding50051 rather than the intended8080. The test fixture subsequently launches its test server on that wrong port.

The new `_container_server_command` uses `docker top <selected container> -eo pid,args`, skips its header, and selects a command by executable basename equal to `gnmi_process`. The port/noTLS checks are restricted to that command. It also supports `--port=<value>`. CONFIG_DB remains authoritative when present; Docker failure, absent server or absent port retain the standard8080/TLS fallback.

## Source-supported correction

Container and process names remain existing constants/derived selections; the change does not introduce user-supplied shell interpolation or new process mutation.

The selected server is not an arbitrary `telemetry` substring: the parser reads the executable token and compares its basename. A telemetry-helper or unrelated command is skipped. The fallback inspects only that matched command for port and TLS state; another host-visible process no longer supplies either value.

Actual [gNMI fixture/caller](https://github.com/sonic-net/sonic-mgmt/blob/125f15cddd6a5ebe86d90f5a36bf6cb1e67d6abb/tests/gnmi/helper.py#L44-L76) builds `/usr/sbin/<process> --port <env port>` after discovering the environment, then uses existing container-scoped process helpers. Thus the correction reaches the launch configuration that formerly conflicted with telemetry's listener. The separate #28145 helper avoids killing the other container's process; these fixes are complementary, not interchangeable.

This change does not itself stop/start a process or verify a listening socket. Those operational fixture paths were inspected as source only.
