## R1 — Bound TLS establishment before reporting gRPC READY

**Introduced in the new implementation.** [The TCP connector](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/grpc.rs#L269-L276) emits `Connected`, mapped to `READY`, immediately after TCP connects. Its five-second timeout covers TCP only; [make_channel](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/grpc.rs#L308-L329) does not configure an endpoint connection timeout.

The locked tonic 0.12.3 [outer connector](https://github.com/hyperium/tonic/blob/v0.12.3/tonic/src/transport/channel/service/connector.rs#L49-L71) performs TLS after the custom connector returns. Its [endpoint](https://github.com/hyperium/tonic/blob/v0.12.3/tonic/src/transport/channel/endpoint.rs#L389-L404) only installs the encompassing timeout when explicitly configured, while [reconnection](https://github.com/hyperium/tonic/blob/v0.12.3/tonic/src/transport/channel/service/reconnect.rs#L84-L102) retains a pending connection future.

With secure GRPCCLIENT configuration, a peer that accepts TCP and stops progressing TLS can leave this connection attempt pending while telemetry reports `READY`. The 0.5-second RPC deadline ends individual calls, not that retained establishment attempt. HTTP/2 keepalive cannot operate before TLS. The connectivity watcher therefore does not produce its expected failure transition solely because those RPCs time out. This is **not** a TLS-authentication bypass: tonic still applies TLS.

**Smallest correction:** bound establishment through TLS, and report readiness only after the transport is usable. Add a TCP-accepting/TLS-stalling failure-and-recovery regression. The existing plaintext refusal/loss and missing-certificate tests do not exercise this case. This is source/dependency inspection, not a locally reproduced failure or measured outage.

**Discussion:** already raised in the existing human review linked above; no duplicate target submission is requested.

## R2 — Keep runtime replay behind pending transceiver events

**Gap in a newly supported path.** [start_tables](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/db.rs#L354-L380) emits newly subscribed tables' existing rows before returning to the existing notification stream.

Start a namespace without mux actors. A first newly configured port's insertion triggers subscription expansion. While those subscriptions are added, a second configured port writes its TRANSCEIVER_INFO SET followed by a command **before the command-table subscription takes effect**. The transceiver notification is buffered, but the command enters initial replay first. [The router](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/daemon.rs#L157-L217) finds no actor and ignores a toggle/probe, or answers a CLI command through a temporary non-mux actor. Creating the real actor later queues initialization only; there is no rescuing notification for the pre-subscription write.

**Smallest correction:** preserve lifecycle-before-command admission during expansion, or retain/reconcile commands for configured ports awaiting actor creation. Test two ports arriving during setup, not just commands written after setup completes. The established-subscription ordering and actor-mailbox FIFO tests do not cover the earlier admission gap. No claim is made that Python supports the entire dynamic-add scenario correctly.

**Discussion:** already raised in the same human review. Avoid duplicate feedback.

## R3 — Configuration removal must revoke an existing actor's hardware-control path

**Introduced compatibility gap; new distinct feedback.** [handle_request](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/actor/mod.rs#L368-L388) dispatches from cached `self.cable`. The actor refreshes classification on [a transceiver SET](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/actor/mod.rs#L410-L452), but the subscribed tables do not include CONFIG_DB MUX_CABLE.

Initialize an active-standby port with a driver, then delete its MUX_CABLE configuration without changing TRANSCEIVER_INFO or physical presence. A queued or subsequent HW_MUX_CABLE_TABLE request still reaches its actor. [toggle_standby and its helpers](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/actor/standby.rs#L223-L398) check state, presence and driver, but not current mux membership, so the vendor toggle still executes. Periodic telemetry also continues using cached classification.

In contrast, the [Python worker](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled/ycable/ycable_utilities/y_cable_helper.py#L3733-L3740) rechecks `check_mux_cable_port_type` at request dispatch and skips a missing row; its telemetry entry point also rechecks configuration. This is specifically configuration removal without a cable event, not an assertion that all Python reconfiguration behavior is correct.

**Smallest correction:** revalidate membership before admitting actionable requests/telemetry, or route configuration invalidation through the actor with explicit ordering. Add a regression deleting MUX_CABLE without a transceiver event and requiring no later driver/RPC action. The reinsertion classification test covers a different trigger.

## Nonblocking notes

**N1 — Syslog backpressure:** [logger::log](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/logger.rs#L80-L113) holds a global mutex during synchronous datagram sends, with a 500-ms timeout and retry. On the two-worker runtime, a stalled logging receiver can delay unrelated actors and timers. The retry is bounded; this is not an unconditional deadlock or a measured RPC deadline violation. Nonblocking logging or a bounded dedicated logging path is a useful follow-up.

**Q1 — Toolchain floor:** Cargo.toml declares Rust 1.80, while the helper image selects 1.99.1. Confirm that the committed dependency selection builds with the declared minimum, or adjust that declaration. No compiler or dependency constraint evaluator was run, so this is not a proven MSRV failure or approval condition.
