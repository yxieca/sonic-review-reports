## Remaining command concerns

### R10 — Make request acquisition and completion ownership coherent (P2)

[handle_cli](https://github.com/sonic-net/sonic-platform-daemons/blob/570200a7ba4b5063db8a827f464e4275de948294/crates/ycabled/src/cli.rs#L184-L247) validates command fields, then obtains the argument row in a separate awaited read. A replacement completed between those reads can still pair old FEC selection with new AN/LT target/mode, causing the wrong operation before later completion checks suppress its answer.

At the other end, [request_current/respond](https://github.com/sonic-net/sonic-platform-daemons/blob/570200a7ba4b5063db8a827f464e4275de948294/crates/ycabled/src/cli.rs#L1333-L1395) checks command and arguments, then awaits response publication, then calls a consumption API protecting **only command fields**. If a same-selector replacement changes arguments during the publication wait, the old answer can be published and the replacement consumed. Even a different selector can receive the old response before its command is preserved; the actual CLI consumer identifies responses by shared port/field rather than a generation.

**Correction:** coherent command-plus-argument acquisition and completion ownership, preventing stale result/response publication as well as improper consumption. Account for APPL_DB/STATE_DB separation; do not assume a single ordinary Redis script can atomically write across those databases. Add gated replacement cases between acquisition reads and during result/response publication. The current driver-delay tests deliberately exercise an earlier boundary, which is now corrected.

This is a narrower residual of [the existing completion discussion](https://github.com/sonic-net/sonic-platform-daemons/pull/944#discussion_r4719070916), also summarized by [the latest review](https://github.com/sonic-net/sonic-platform-daemons/pull/944#pullrequestreview-6088922990). It is not a claim that Redis fails to execute the script atomically or a locally reproduced device incident. No Lua predicate evaluator was run; the source finding concerns the request information excluded from the consumption API and separate caller publication steps.

### R13 — Do not classify failed ownership reads as withdrawal (P2)

[RedisDb::get](https://github.com/sonic-net/sonic-platform-daemons/blob/570200a7ba4b5063db8a827f464e4275de948294/crates/ycabled/src/db.rs#L643-L656) logs a failed HGETALL and returns None. The new ownership decisions in `handle_cli`, `write_result` and `request_current` cannot distinguish failed observation from a successfully observed missing/replaced row.

After successful command delivery or hardware execution, a validation read can fail while pub/sub remains healthy. Completion is skipped, the actor moves on and the valid command remains pending without another notification. A failed result-ownership check can omit result data, while later successful response checks permit a success response and consumption. Argument-read failures likewise become default empty maps rather than an explicit recovery decision.

**Correction:** fallible correctness-critical reads; separate absence/mismatch from transport errors. Preserve an already executed operation for bounded completion retry or enter explicit recovery without blindly repeating non-idempotent hardware effects. Add isolated read failures after successful initial delivery and during result/response ownership checks. Fixed subscription/replay error handling is useful counterevidence, but does not cover these actor-side reads.

This stable concern extends to the newly added completion gate. No dedicated target inline for the precise ownership-read failure was present in the inspected discussion; distinct feedback remains useful.

### R14 — Confirm required publication before consuming a command (P2)

[RedisDb::set](https://github.com/sonic-net/sonic-platform-daemons/blob/570200a7ba4b5063db8a827f464e4275de948294/crates/ycabled/src/db.rs#L675-L690) returns no success status when HSET fails. `respond` still proceeds to command consumption. A failed STATE_DB response write followed by a successful APPL_DB consume therefore leaves no answer and no pending command. A failed required result write can similarly be followed by a success response with missing/stale data.

**Correction:** fallible required publication and consumption only after confirmed completion; define recovery for ambiguous write outcomes without indiscriminately repeating the driver operation. Separate response/result connection failure from pub/sub loss in controls. A gated successful memory-DB write is not a failed-write test, and MONITOR records commands rather than proof of successful effects.

This inherited backend behavior was previously qualified as Q2; the current reliable-completion path and independent source checks now establish a concrete source-level fix requirement. It is already summarized in [review 6088922990](https://github.com/sonic-net/sonic-platform-daemons/pull/944#pullrequestreview-6088922990). It is conditional P2, not an observed Redis outage, and not uniquely introduced by this increment.

## Remaining source concerns

### R10 — Preserve replacement ownership through in-flight CLI completion (P2)

[Admission](https://github.com/sonic-net/sonic-platform-daemons/blob/8c34cb37da83f45f3108eeeac74e9f1af2d151e4/crates/ycabled/src/cli.rs#L183-L207) now checks the command before execution. But [respond](https://github.com/sonic-net/sonic-platform-daemons/blob/8c34cb37da83f45f3108eeeac74e9f1af2d151e4/crates/ycabled/src/cli.rs#L1302-L1321) still receives no request snapshot, writes the shared response and unconditionally deletes the current command key.

FEC request A can pass admission and enter a slow driver call. The CLI times out and writes replacement AN/LT request B, which waits in the actor mailbox. When A returns, it publishes A's response and deletes B's key. B then reaches the new admission check, sees no row and is skipped. The old response can also be mistaken for B's answer. The actual CLI producer's timeout, cleanup and argument-before-command writes make this a reachable serial replacement case, not only unsupported simultaneous clients.

**Correction:** retain request ownership through result/response publication and atomically consume only that request; preserve replacements and their own answers. A final GET followed by unconditional DEL still races. Apply the same ownership rule to detached firmware completion. The new queued-replacement test does not start A's driver operation before replacing it; add that held-call regression.

Already raised: https://github.com/sonic-net/sonic-platform-daemons/pull/944#discussion_r4719070916

### R11 — Serialize final epoch validation with completed telemetry publication (P2)

[Active telemetry](https://github.com/sonic-net/sonic-platform-daemons/blob/8c34cb37da83f45f3108eeeac74e9f1af2d151e4/crates/ycabled/src/actor/active.rs#L370-L375) and [its normal publication](https://github.com/sonic-net/sonic-platform-daemons/blob/8c34cb37da83f45f3108eeeac74e9f1af2d151e4/crates/ycabled/src/actor/active.rs#L463-L470), plus [standby telemetry](https://github.com/sonic-net/sonic-platform-daemons/blob/8c34cb37da83f45f3108eeeac74e9f1af2d151e4/crates/ycabled/src/actor/standby.rs#L532-L546), check the epoch and then await the DB write without the lifecycle lock.

Lifecycle requests hold the actor call lock and advance the epoch, but these final writes do not participate. An old pass can pass validation, remain pending before DB submission during connection acquisition/recovery, and publish after reinitialization has advanced the epoch and written replacement state. This is a check/publication ordering gap, not a partially written HSET or proof that every delayed Redis response reorders writes.

**Correction:** hold the same per-port lifecycle lock through final epoch validation and completed write for normal and placeholder publications. Keep collection RPCs outside that final critical section. Add a gated DB-publication regression; the existing memory DB completes writes without a suspension point and queued-pass tests cover earlier invalidation.

Already raised: https://github.com/sonic-net/sonic-platform-daemons/pull/944#discussion_r4719070833

### R13 — Distinguish command-validation read failure from replacement/absence (P2)

[The new current-command check](https://github.com/sonic-net/sonic-platform-daemons/blob/8c34cb37da83f45f3108eeeac74e9f1af2d151e4/crates/ycabled/src/cli.rs#L188-L202) uses `Db::get`. [RedisDb::get](https://github.com/sonic-net/sonic-platform-daemons/blob/8c34cb37da83f45f3108eeeac74e9f1af2d151e4/crates/ycabled/src/db.rs#L626-L640) logs a failed HGETALL and returns None, indistinguishable from a withdrawn command.

The subscription can successfully read/deliver a valid command, then its execution-time revalidation read can fail while pub/sub remains healthy. The handler skips it as replaced/withdrawn; the valid APPL_DB row remains but its notification has been consumed, with no retry/fatal recovery on that path. This is a newly introduced correctness-critical read, separate from the now-fixed subscription replay.

**Correction:** a fallible validation read; absence/mismatch must be a successfully observed state, not a DB error. Retry in order or invoke the established recovery policy. Add a control that fails only the later validation read after successful delivery. This distinct concern is not merely another copy of the replay finding.

## R1 — Bound TLS establishment before reporting gRPC READY

**Introduced in the new implementation.** [The TCP connector](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/grpc.rs#L269-L276) emits `Connected`, mapped to `READY`, immediately after TCP connects. Its five-second timeout covers TCP only; [make_channel](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/grpc.rs#L308-L329) does not configure an endpoint connection timeout.

The locked tonic 0.12.3 [outer connector](https://github.com/hyperium/tonic/blob/v0.12.3/tonic/src/transport/channel/service/connector.rs#L49-L71) performs TLS after the custom connector returns. Its [endpoint](https://github.com/hyperium/tonic/blob/v0.12.3/tonic/src/transport/channel/endpoint.rs#L389-L404) only installs the encompassing timeout when explicitly configured, while [reconnection](https://github.com/hyperium/tonic/blob/v0.12.3/tonic/src/transport/channel/service/reconnect.rs#L84-L102) retains a pending connection future.

With secure GRPCCLIENT configuration, a peer that accepts TCP and stops progressing TLS can leave this connection attempt pending while telemetry reports `READY`. The 0.5-second RPC deadline ends individual calls, not that retained establishment attempt. HTTP/2 keepalive cannot operate before TLS. The connectivity watcher therefore does not produce its expected failure transition solely because those RPCs time out. This is **not** a TLS-authentication bypass: tonic still applies TLS.

**Smallest correction:** bound establishment through TLS, and report readiness only after the transport is usable. Add a TCP-accepting/TLS-stalling failure-and-recovery regression. The existing plaintext refusal/loss and missing-certificate tests do not exercise this case. This is source/dependency inspection, not a locally reproduced failure or measured outage.

**Discussion:** already raised in the existing human review linked above; no duplicate target submission is requested.

## R2 — Keep runtime replay behind pending transceiver events

**Gap in a newly supported path.** [start_tables](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/db.rs#L354-L380) emits newly subscribed tables' existing rows before returning to the existing notification stream.

Start a namespace without mux actors. A first newly configured port's insertion triggers subscription expansion. While those subscriptions are added, a second configured port writes its TRANSCEIVER_INFO SET followed by a command **before the command-table subscription takes effect**. The transceiver notification is buffered, but the command enters initial replay first. [The router](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/daemon.rs#L157-L217) finds no actor and ignores a toggle/probe, or answers a CLI command through a temporary non-mux actor. Creating the real actor later queues initialization only; there is no rescuing notification for the pre-subscription write.

**Smallest correction:** preserve lifecycle-before-command admission during expansion, or retain/reconcile commands for configured ports awaiting actor creation. Test two ports arriving during setup, not just commands written after setup completes. The established-subscription ordering and actor-mailbox FIFO tests do not cover the earlier admission gap. No claim is made that Python supports the entire dynamic-add scenario correctly.

**Discussion:** already raised in the same human review. Avoid duplicate feedback.

## R3 — Configuration removal must revoke an existing actor's hardware-control path

**Introduced compatibility gap; new distinct feedback.** [handle_request](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/actor/mod.rs#L368-L388) dispatches from cached `self.cable`. The actor refreshes classification on [a transceiver SET](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/actor/mod.rs#L410-L452), but the subscribed tables do not include CONFIG_DB MUX_CABLE.

Initialize an active-standby port with a driver, then delete its MUX_CABLE configuration without changing TRANSCEIVER_INFO or physical presence. A queued or subsequent HW_MUX_CABLE_TABLE request still reaches its actor. [toggle_standby and its helpers](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/actor/standby.rs#L223-L398) check state, presence and driver, but not current mux membership, so the vendor toggle still executes. Periodic telemetry also continues using cached classification.

In contrast, the [Python worker](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled/ycable/ycable_utilities/y_cable_helper.py#L3733-L3740) rechecks `check_mux_cable_port_type` at request dispatch and skips a missing row; its telemetry entry point also rechecks configuration. This is specifically configuration removal without a cable event, not an assertion that all Python reconfiguration behavior is correct.

**Smallest correction:** revalidate membership before admitting actionable requests/telemetry, or route configuration invalidation through the actor with explicit ordering. Add a regression deleting MUX_CABLE without a transceiver event and requiring no later driver/RPC action. The reinsertion classification test covers a different trigger.

## Nonblocking notes

**N1 — Syslog backpressure:** [logger::log](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/logger.rs#L80-L113) holds a global mutex during synchronous datagram sends, with a 500-ms timeout and retry. On the two-worker runtime, a stalled logging receiver can delay unrelated actors and timers. The retry is bounded; this is not an unconditional deadlock or a measured RPC deadline violation. Nonblocking logging or a bounded dedicated logging path is a useful follow-up.

**Q1 — Toolchain floor:** Cargo.toml declares Rust 1.80, while the helper image selects 1.99.1. Confirm that the committed dependency selection builds with the declared minimum, or adjust that declaration. No compiler or dependency constraint evaluator was run, so this is not a proven MSRV failure or approval condition.
