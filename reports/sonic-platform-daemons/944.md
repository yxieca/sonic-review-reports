## Blocking source concerns

All links below point to the reviewed head; priorities describe conditional source/integration risk, not a measured deployed failure.

### R1 — Require a complete initial HTTP/2 frame before READY

[MonitoredIo::poll_read](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/grpc.rs#L293-L322) removes its establishment deadline and emits Connected on **any nonempty read**. A single byte of a SETTINGS header followed by a stall therefore reports READY before a complete frame is accepted and disables this deadline.

The selected h2 0.4.21 parser uses a length-delimited frame reader; a byte is not a complete SETTINGS frame. Merely waiting for its client-handshake return is not sufficient either: that API does not wait for the server's initial SETTINGS. The current tests exercise no HTTP/2 bytes and stalled/failed TLS, not header/payload fragmentation.

**Correction:** retain the bound through complete valid initial SETTINGS acceptance or an equivalent protocol-aware readiness signal; add fragmented-header/payload controls over plaintext and TLS. RPCs still have 0.5-second deadlines. Missing failure notification can delay a linkmgrd probe; it is not evidence of an immediate switchover or permanent traffic outage. Actual linkmgrd consumes `failure` as a failure-handling notification, not an active/standby state.

Already raised: https://github.com/sonic-net/sonic-platform-daemons/pull/944#discussion_r4717049636

### R3 — Revoke hardware control when mux configuration is removed

[The existing-actor fast path](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/daemon.rs#L245-L271) returns before querying current MUX_CABLE. [Actor dispatch](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/actor/mod.rs#L348-L393) still uses cached cable type.

Initialize a port, delete MUX_CABLE while physical presence and TRANSCEIVER_INFO remain unchanged, then deliver a queued or subsequent toggle. The existing driver/cached classification still admits the hardware call. Refreshing type on insertion does not cover configuration deletion alone. Python rechecks membership at ordinary toggle/probe dispatch and telemetry.

**Correction:** revalidate actionable admission and telemetry or deliver ordered configuration invalidation through the actor. Test configuration removal without a transceiver event and require no subsequent driver/RPC action. This stable concern remains open; the author correction addressed R1/R2, not this condition.

### R4 — Bootstrap request ingress for an already-inserted first mux port

[Daemon::subscribe](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/daemon.rs#L138-L172) subscribes request tables only if actors already exist. A namespace beginning with no mux actors can later configure an already-inserted port and issue a command, but neither request tables nor MUX_CABLE changes are subscribed. The request cannot reach the new on-demand actor path.

**Correction:** enable appropriate request ingress independently, or observe configuration changes to activate it. Test zero initial actors, an existing transceiver row, then configuration plus request without another insertion. Python has a related conditional-worker limitation; this is a gap in the new claimed first-request-supported path, not an invented Python regression.

Already raised: https://github.com/sonic-net/sonic-platform-daemons/pull/944#discussion_r4717049507

### R5 — Do not miss cable removal during startup

[Startup](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/daemon.rs#L435-L468) starts actors and waits for initialization before subscribing TRANSCEIVER_INFO. A port that initialized successfully can be removed while another port prolongs this wait. Its deleted row has nothing to replay; the DEL is lost. A later same-configured-type replacement SET reaches an actor still initialized and [is ignored](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/actor/mod.rs#L413-L443), retaining the previous driver even when vendor/model changed.

**Correction:** establish transceiver ingress before starting initialization and buffer each event behind that port's Init. A full-startup removal/replacement regression is needed. The 30-second wait bounds the window, not its correctness. Python has the same family of startup limitation; the replacement's design specifically promises to close it. No physical wrong-driver incident was reproduced here.

Already raised: https://github.com/sonic-net/sonic-platform-daemons/pull/944#discussion_r4717049549

### R6 — Recover unread notification rows instead of consuming them

[events_of](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/db.rs#L407-L500) logs a failed HGETALL and continues. If the command connection fails while pub/sub remains healthy, a consumed one-shot notification never reaches its actor. Reconnection alone does not recreate it.

The locked redis 0.27.6 command manager returns the failed command result and initiates reconnection; its configured connection retries are not proof that this failed notification is automatically replayed. The inspected swss-common subscriber backend propagates command errors rather than treating them as absent rows; the Python worker can consequently terminate and recover instead of silently skipping that command.

**Correction:** retain/retry unread notifications in order or propagate them to a defined recovery policy. Preserve changes-only peer requests explicitly: restart alone will not replay tables deliberately excluded from startup replay. Add split command-connection/pub-sub failure coverage. This gap existed in the earlier Rust implementation too; it is not newly caused solely by batching.

Already raised: https://github.com/sonic-net/sonic-platform-daemons/pull/944#discussion_r4717049593

### R7 — Implement the documented early-failure restart policy

[main](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/main.rs#L16-L61) and [subscription loss](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/daemon.rs#L89-L97) exit immediately. The documented pmon supervisor uses startsecs=10 with finite default startup retries. Repeated failures before successful startup can exhaust retries, leaving FATAL even after the external problem clears.

**Correction:** persistent startup Redis availability retry and a shared early-failure policy delaying fatal termination to the documented safe lifetime, interruptible by shutdown. Apply it consistently to startup, panic and subscription-loss paths. Finite command-manager connection retries do not cover every early failure; this report does not claim every refused Redis connection exits within ten seconds. The daemon is not selected by the inspected current pmon template.

Already raised: https://github.com/sonic-net/sonic-platform-daemons/pull/944#discussion_r4717049683

### R8 — Bound persistent-hang mailbox growth without restoring silent drops

[PortActor::spawn/run](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/actor/mod.rs#L296-L331) uses an unbounded channel and awaits the current handler. With a driver call held indefinitely, continuing probes/toggles accumulate owned messages. Backlog logging is evaluated on the next receive, so it cannot warn during that held handler.

**Correction:** bounded ordered coalescing/reconciliation preserving lifecycle events and latest command/state semantics, as the design describes. Cover ongoing notifications to a held port and healthy-port progress. The original 256-entry silent-drop defect is fixed for finite bursts; this is a different overload boundary. No OOM or production frequency was measured, and silently dropping events or restarting every healthy port is not the requested remedy.

### R9 — Enforce one actual in-flight firmware download per port

[cli_download_firmware](https://github.com/sonic-net/sonic-platform-daemons/blob/2401414a5f4e27a2ee62b2e2c2b656e3d8c24980/crates/ycabled/src/cli.rs#L582-L663) starts detached work for every accepted download. No per-port reservation survives until the underlying vendor call returns. The bridge gives its admission slot back after 10 ms, but a held call still retains its blocking worker; repeated requests can therefore exceed the claimed per-port resource bound.

**Correction:** reserve single-flight state before spawning, retain it until actual return across cable changes, and reject another request using the documented error response. Test duplicates/replayed requests and healthy-port progress while a download is held. Do not hold the ordinary request lock for the entire download. Python also allows a thread per download; this is an inherited behavior conflicting with the replacement's explicit single-flight design, not a new Python-parity regression or a reproduced pool-exhaustion incident.

## R1 — Bound TLS establishment before reporting gRPC READY

**Introduced in the new implementation.** [The TCP connector](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/grpc.rs#L269-L276) emits `Connected`, mapped to `READY`, immediately after TCP connects. Its five-second timeout covers TCP only; [make_channel](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/grpc.rs#L308-L329) does not configure an endpoint connection timeout.

The locked tonic 0.12.3 [outer connector](https://github.com/hyperium/tonic/blob/v0.12.3/tonic/src/transport/channel/service/connector.rs#L49-L71) performs TLS after the custom connector returns. Its [endpoint](https://github.com/hyperium/tonic/blob/v0.12.3/tonic/src/transport/channel/endpoint.rs#L389-L404) only installs the encompassing timeout when explicitly configured, while [reconnection](https://github.com/hyperium/tonic/blob/v0.12.3/tonic/src/transport/channel/service/reconnect.rs#L84-L102) retains a pending connection future.

With secure GRPCCLIENT configuration, a peer that accepts TCP and stops progressing TLS can leave this connection attempt pending while telemetry reports `READY`. The 0.5-second RPC deadline ends individual calls, not that retained establishment attempt. HTTP/2 keepalive cannot operate before TLS. The connectivity watcher therefore does not produce its expected failure transition solely because those RPCs time out. This is **not** a TLS-authentication bypass: tonic still applies TLS.

**Smallest correction:** bound establishment through TLS, and report readiness only after the transport is usable. Add a TCP-accepting/TLS-stalling failure-and-recovery regression. The existing plaintext refusal/loss and missing-certificate tests do not exercise this case. This is source/dependency inspection, not a locally reproduced failure or measured outage.

**Discussion:** already raised in the existing human review linked above; no duplicate target submission is requested.

## R2 — Keep runtime replay behind pending transceiver events

**Gap in a newly supported path.** [start_tables](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/db.rs#L354-L380) emits newly subscribed tables' existing rows before returning to the existing notification stream.

Start a namespace without mux actors. A first newly configured port's insertion triggers subscription expansion. While those subscriptions are added, a second configured port writes its TRANSCEIVER_INFO SET followed by a command **before the command-table subscription takes effect**. The transceiver notification is buffered, but the command enters initial replay first. [The router](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/daemon.rs#L157-L217) finds no actor and ignores a toggle/probe, or answers a CLI command through a temporary non-mux actor. Creating the real actor later queues initialization only; there is no rescuing notification for the pre-subscription write.

**Smallest correction:** preserve lifecycle-before-command admission during expansion, or retain/reconcile commands for configured ports awaiting actor creation. Test two ports arriving during setup, not just commands written after setup completes. The established-subscription ordering and actor-mailbox FIFO tests do not cover the earlier admission gap. No claim is made that Python supports the entire dynamic-add scenario correctly.

**Discussion:** already raised in the same human review. Avoid duplicate feedback.

## R3 — Configuration removal must revoke an existing actor's hardware-control path

**Introduced compatibility gap; new distinct feedback.** [handle_request](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/actor/mod.rs#L368-L388) dispatches from cached `self.cable`. The actor refreshes classification on [a transceiver SET](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/actor/mod.rs#L410-L452), but the subscribed tables do not include CONFIG_DB MUX_CABLE.

Initialize an active-standby port with a driver, then delete its MUX_CABLE configuration without changing TRANSCEIVER_INFO or physical presence. A queued or subsequent HW_MUX_CABLE_TABLE request still reaches its actor. [toggle_standby and its helpers](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled-rs/src/actor/standby.rs#L223-L398) check state, presence and driver, but not current mux membership, so the vendor toggle still executes. Periodic telemetry also continues using cached classification.

In contrast, the [Python worker](https://github.com/sonic-net/sonic-platform-daemons/blob/fe17f2eb76d6574ef6bcdb4bb3f1a5a20f1b4036/sonic-ycabled/ycable/ycable_utilities/y_cable_helper.py#L3733-L3740) rechecks `check_mux_cable_port_type` at request dispatch and skips a missing row; its telemetry entry point also rechecks configuration. This is specifically configuration removal without a cable event, not an assertion that all Python reconfiguration behavior is correct.

**Smallest correction:** revalidate membership before admitting actionable requests/telemetry, or route configuration invalidation through the actor with explicit ordering. Add a regression deleting MUX_CABLE without a transceiver event and requiring no later driver/RPC action. The reinsertion classification test covers a different trigger.
