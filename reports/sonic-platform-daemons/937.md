## Summary

CPO-first lookups now use each port's get_xcvr_api rather than treating a CPO port as absent via get_sfp. The extracted generic VDM publisher preserves freeze/statistic/basic/flags ordering and remains the same sequence for pluggable ports. CPO thresholds inherit standard VDMDBUtils, matching the standard VDM table schema, and temperature snapshots are independently cached by OE/ELS sharing group per pass. Stop/error paths retain the last known temperature rather than publishing a fabricated successful read.

The new CPO path does invoke a bank-specific port object, but a bank-specific API object does not itself make unchanged raw page offsets bank-aware. That distinction is the blocking source integration issue. The new test's per-port MagicMock values bypass the real reader and therefore do not validate different banks' published readings.

## R1 — per-bank object lookup does not repair raw VDM offsets

**A1.** New `CpoDomInfoUpdateTask.collect_and_publish_data` calls `publish_vdm_data` for every physical CPO port. New CPOVDMDBUtils inherits VDMDBUtils, which resolves physical port and calls its VDM getters for thresholds/flags. VDMUtils delegates to the port -> OE CmisApi -> CmisVdmApi.

**A2.** Independently fetched common790 head7b1dccafb8498ee3c30b200e623219d364859aad and its base014f72fa6907cc18890c767d697aae43f2eb9fce have identical `cmisVDM.py`. `_read_vdm_descriptor_page` usespage*128+128; value/threshold reads likewise usepage*128+128; flag read uses0x2c*128+128. None includes `xcvr_eeprom.mem_map.bank`. Actual XcvrEeprom.read_raw passes the offset unchanged to the reader. The reviewed banked platform transport decodes bank from the linear offset, so these offsets selectbank0 even for an OE object withbank1/2/3. CmisPage.linear_offset provides the existing bank-aware coordinate convention, but this raw reader does not use it.

**A3.** Under the proposed multi-bank CPO integration, the publisher can placebank0values/thresholds/flags in later banks' logical rows and miss a flag only latched onbank1. Coordinator-only exact extracted raw-reader/decoder/publisher methods with virtual bank memory verify four API objects with bank0–3 all publish10 from bank0, while the bank-coordinate control distinguishes10/20/30/40. Threshold and bank1-only flag source paths use the same omitted-bank offsets. This is an inert source control—not physical EEPROM access, a native pytest run or a deployed image observation.

**B1.** The common raw-reader omission is inherited. This PR newly enables that reader through everyCPO bank and publishes the results as bank-specific data; the extra consequence is introduced by this consumer activation. Existing single-bank pluggable semantics are not claimed to regress.

**B2.** The new test assigns values from physical-portMagicMocks, so it establishes publisher routing but removes the actual bank-dependent read. Distinct port objects and correct DB names alone do not prove correct bytes. No daemons package pins a common commit here; the report therefore does not assume common790 or any latesthead is installed. It states the inspected compatibility contract and the required source dependency before enabling this path, not an unverified deployment claim.

## N1 — best-effort post-powerup metadata needs a later retry

The new `post_port_info_after_power_up_to_db` returns when the hook yields no data or theTRANSCEIVER_INFO row does not exist; exceptions are logged then swallowed. Its caller still moves the port toREADY, as intended for link bring-up. All actual new calls occur at READY-entry branches; the regular READY path does not retry missinginfo. The independently inspected NVIDIA common hook can returnNone for unavailable telemetry and exposes oe_sn only through this post-powerup hook, not ordinarytransceiver_info, so a transient first failure can leave that field absent until another lifecycle transition.

This is a new metadata reliability gap, **not** a reason to delay otherwise healthy link-up or an observed service outage. Keep it **nonblocking P3**: track pending metadata and retry through a bounded normal path without repeating datapath operations. Tests cover no-data/error/absent-row helper no-ops, but not later recovery without a flap. Exact helper and READY-terminal predicate controls separately show first missing-data/row cases write nothing, a healthy control writes once, and regular READY processing returns before the helper; no live datapath or database was used. [Existing human thread](https://github.com/sonic-net/sonic-platform-daemons/pull/937#discussion_r4679064951) and the separate ownership-placement discussion are credited.
