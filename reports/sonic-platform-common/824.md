## Summary

This adds a source-owned pure-Python Bazel wheel and independent integration-test root around the existing platform API source. It preserves the existing setuptools distribution/version/requirements and type-file selection, while avoiding a production dependency back on the consuming image.

The source suite retains original fixture semantics, runs the type gates and records test inventory. ## Incremental action accounting and restoration

[Incremental checker](https://github.com/sonic-net/sonic-platform-common/blob/c70f9594b30780851fa4f0e7285c9c6885bede4d/tests/bazel/wheel_incremental.py) changes one Y-cable constant, rebuilds and checks the installed value. File names/modes must match; only the edited Python member and RECORD may differ. It restores original bytes on failure and requires the restored wheel to match the baseline digest.

No-op acceptance requires zero uncached spawns and no action beyond one workspace-status bookkeeping action. Internal writes and cache-served wheel actions are accounted separately from process execution; they cannot hide behind “zero uncached processes.” The source fixtures and negative controls cover malformed/missing accounting, duplicate members, changed modes, unrelated payloads and checkout trust.

Coordinator checks used only exact AST-selected guards and dictionary records: workspace-only bookkeeping was accepted, and FileWrite, cache-served PyWheel and uncached-spawn records were rejected. This was not the authored unittest suite or a Bazel action run.

## Nonblocking clarifications

[Wheel declaration](https://github.com/sonic-net/sonic-platform-common/blob/c70f9594b30780851fa4f0e7285c9c6885bede4d/BUILD.bazel#L33-L61) preserves runtime-significant name/version/requirements but omits setup.py’s descriptive maintainer, maintainer-email, classifiers and keywords. The selected packaging rule supports these fields; the installed contract checker does not compare all of them.

**Consequence:** distribution-description metadata differs between the two build paths. It is not a missing API or runtime payload.

**Optional correction:** copy those literal setup attributes to py_wheel if full descriptive metadata parity is intended. This can follow separately; do not make native/hardware qualification a prerequisite for a metadata change.

### N2 — Distinguish generator templates from installed owner payload

The PR body says the wheel includes templates. The owner wheel selects Python/API type files and licenses; `generator/**`, including generator templates, is a source-test input rather than wheel payload. That matches setup.py’s installation contract.

Clarify the wording as “generator templates are build/test inputs; the wheel carries owner API source and type files.” This is a description correction, not a request to package unrelated templates or an asserted installed-data loss.
