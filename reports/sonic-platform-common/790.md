## Summary

The change provides separate vendor CDB maps and module-wide reentrant lock/target routing, correctly holds telemetry command/reply/extended reads under one lock, keeps untargeted ELS9018 routing explicit, and gates OE telemetry on supported-and-valid masks. Factories now pass vendor maps and enable CDB firmware deliberately for NVIDIA endpoints; the new package is listed in setup.py. Firmware transfers expose lazy per-block progress, preserve underlying failure status before Abort, and refresh the API between run and commit. Tests cover many selector, lock, encoding, capability, bank and generator cases, but none was executed here.

One newly added cancellation path does not meet its own idle-before-Abort contract. The lower CMIS failed-download path already checks the return value; the new mixin's generator-close path does not. This is a precise new source gap, not a requirement to invent a platform probe or future hardware framework.

## R1 — cancellation sends a new CDB command without confirmed idle

**A1.** New `CdbFirmwareMixin._abort_download` calls `api.cdb_fw_hdlr.wait_for_cdb_status()` but ignores the returned completion result, then calls `abort_fw_download`. Actual `CdbCmdHandler.wait_for_cdb_status` returns `[False,status]` on timeout, including a still-busy status or no usable status. It does not raise on that ordinary failure.

**A2.** `_download` catchesBaseException while its generator yields blocks and invokes this cancellation helper. Closing the generator (or KeyboardInterrupt/OSError during transfer) therefore reaches the unguarded Abort. `CdbFwHandler.abort_fw_download` calls `send_cmd(CDB_ABORT_FIRMWARE_DOWNLOAD_CMD)`, which writes the new command **before** its own completion wait. The outer module lock excludes other clients; it does not make an already executing device command idle.

**A3.** Cancellation can dispatch Abort into a busy/unreadable mailbox even though waiting did not establish readiness; the module can reject it and cancellation is not completed as promised. The original interruption is preserved, but the helper does not report that no safe idle point was reached. No physical state corruption or observed abort outcome is asserted; the demonstrated source consequence is the unauthorized-by-protocol next command after a failed wait.

**B1.** `cdb_firmware.py` and its close/interrupt cancellation path are new versus the exact target base. The generic `CmisCdbFw._abort_fw_download` added in this same PR correctly checks `wait_for_cdb_status()[0]` and returns before Abort whenFalse. The new mixin leaves that protection inconsistent in a separately reachable path.

**B2.** No-abort-unsupported, successful cancellation, original exception preservation and per-block RuntimeError handling are covered by authored tests. The cancellation test `test_abort_waits_for_the_pending_command` asserts only call order with aMagicMock wait result; it does not coverFalse. The separate failed-block CMIS test does coverFalse, but exercises a different helper. Missing target-selection can also yieldNone via CdbTargetHandler, so checking the concrete result safely matters.

[Immutable cancellation and caller](https://github.com/sonic-net/sonic-platform-common/blob/7b1dccafb8498ee3c30b200e623219d364859aad/sonic_platform_base/sonic_xcvr/cdb_firmware.py#L105-L144), [wait result](https://github.com/sonic-net/sonic-platform-common/blob/7b1dccafb8498ee3c30b200e623219d364859aad/sonic_platform_base/sonic_xcvr/cdb/cdb.py#L59-L92), [protected parallel helper](https://github.com/sonic-net/sonic-platform-common/blob/7b1dccafb8498ee3c30b200e623219d364859aad/sonic_platform_base/sonic_xcvr/api/public/cdb_fw.py#L205-L219).

Smallest correction: inspect the actual wait return/completion status; issue Abort only on a verified nonbusy completion, otherwise log cancellation-not-completed while preserving the original interruption. Add a generator-close busy-timeout/unreadable case and an idle success control through the mixin helper. Coordinator-only exact extracted generator-close and wait methods with fake handlers verify both busy-timeout and unreadable [False,status] results still invoke Abort, as does an idle control. The same-PR protected parallel helper does not Abort for False results and does for an idle success control. No actual firmware transfer, native module import or device command was executed. [Existing human thread](https://github.com/sonic-net/sonic-platform-common/pull/790#discussion_r4679063893) credited; no duplicate target feedback.

## R2 — target-selection failure breaks the new guarded cleanup result contract

**Kind / priority:** introduced wrapper/cleanup interaction, P2. **Disposition:** open; newly identified.

The [target handler](https://github.com/sonic-net/sonic-platform-common/blob/7b1dccafb8498ee3c30b200e623219d364859aad/sonic_platform_base/sonic_xcvr/api/nvidia/cpo_cdb.py#L185-L218) explicitly returns `None` for ordinary method calls when target selection fails. That includes `wait_for_cdb_status`. The new [guarded abort helper](https://github.com/sonic-net/sonic-platform-common/blob/7b1dccafb8498ee3c30b200e623219d364859aad/sonic_platform_base/sonic_xcvr/api/public/cdb_fw.py#L205-L219) immediately indexes the result with `[0]`.

**Condition/consequence:** if the NVIDIA handler has initialized and Abort is supported, but target selection becomes unavailable during failed-start/block cleanup, the guard raises TypeError instead of handling unavailable readiness. The actual failed-start caller invokes this helper before returning its intended failure tuple; cleanup can therefore replace the useful command failure with an unrelated exception. The synchronous block wrapper catches RuntimeError, not this TypeError.

**Base and counterevidence:** native unwrapped waits return a two-element list, so a `[False,None]` timeout test alone does not cover the new target wrapper's `None`. Both the wrapper and the indexed guard are introduced here. The guard is a useful improvement for ordinary busy waits and should be retained, not removed.

**Source controls:** coordinator-only exact wrapper, failed-start caller and abort helper with fake target selection produce TypeError on selection failure; a successful-selection control with failed readiness returns the intended `(False, info)` result without invoking an unsafe next command. No real target register, firmware mailbox or device operation was used.

**Smallest correction:** normalize the wrapper's failed wait to the native result shape or validate unavailable results before indexing/unpacking. Preserve the original firmware failure and add a wrapper-to-cleanup regression, not only an unwrapped mock-result test.

## R3 — newly CDB-capable ELS firmware APIs lack the inherited password-fallback hook

**Kind / priority:** introduced API-composition gap, P2. **Disposition:** open; newly identified.

The [new ELS inheritance](https://github.com/sonic-net/sonic-platform-common/blob/7b1dccafb8498ee3c30b200e623219d364859aad/sonic_platform_base/sonic_xcvr/api/public/elsfp.py#L60-L74) adds CmisCdbFw to ElsfpApi, which otherwise derives from XcvrApi and CdbCapableMixin—not CmisApi. Its inherited [get_module_fw_info](https://github.com/sonic-net/sonic-platform-common/blob/7b1dccafb8498ee3c30b200e623219d364859aad/sonic_platform_base/sonic_xcvr/api/public/cdb_fw.py#L109-L147) calls `self.enter_password_via_memory` after a firmware-info password error persists through the CDB-password retry. That method is supplied by CmisApi, not by the new ELS hierarchy or NVIDIA target mixin.

**Condition/consequence:** when that supported error branch is reached on an ELS API, it raises AttributeError instead of attempting an explicitly supported fallback or returning structured failure. The platform-facing firmware-info method does not translate it into its documented operational result.

**Base and counterevidence:** successful firmware-info retrieval and a successful first password retry avoid the branch. The fallback existed for CMIS, whose class supplies the method; this PR newly exposes it through ELS without satisfying its dependency. This does not claim current SPC6 hardware necessarily requires memory-password fallback.

**Source controls:** exact inherited firmware-info source with fake repeated password errors produces AttributeError without the hook. An explicit unsupported-hook control returns the expected structured failure. The complete relevant ELS/API/target hierarchy was checked for the missing method; no password, EEPROM or firmware write was executed.

**Smallest correction:** define an explicit shared password-fallback hook with a controlled unsupported/failure result where appropriate. Establish the NVIDIA ELS target/address contract before implementing any write; blindly copying CMIS's memory write into a mirror-mapped ELS API is not justified. Add an ELS inheritance/error-path regression.


## Q1 — temperature alarm register authority remains unresolved

`NvidiaCpoElsCmisApi.get_non_banked_elsfp_dom_flags` reads `consts.MODULE_FLAG_BYTE3` and describes byte11's high nibble. Actual new `NvidiaCpoElsCmisMemMap` registers the standard lower page through `NvidiaCpoElsB0MirrorPage`, shifting sub128 offsets intoB0 upper memory; the field resolvesB0:139. The map separately registers live byte3/module state,24/custom temperature and16/voltage, but no standalone live byte11 flag field. Thus documentation and effective field routing differ.

The authored per-bit test stubs the field-name read, bypassing address selection; the mirror mapping itself is deliberately used for other fields. This proves source routing/documentation mismatch, **not which hardware register is authoritative or an observed lost alarm. Coordinator-only exact address/API controls with differing in-memory values reproduce live-only false and mirror-only true; those controls establish source routing, not physical authority**. Retain [the human question](https://github.com/sonic-net/sonic-platform-common/pull/790#discussion_r4679063884), request the SPC6 register contract and a differing-live/mirror control, and coordinate clear-on-read ownership only if live byte11 is indeed the required source. Do not make an unverified register-authority assumption a second blocking hardware defect.

[API read](https://github.com/sonic-net/sonic-platform-common/blob/7b1dccafb8498ee3c30b200e623219d364859aad/sonic_platform_base/sonic_xcvr/api/nvidia/cpo_els.py#L111-L129), [mirror addressing](https://github.com/sonic-net/sonic-platform-common/blob/7b1dccafb8498ee3c30b200e623219d364859aad/sonic_platform_base/sonic_xcvr/mem_maps/nvidia/cpo_els.py#L63-L75).
