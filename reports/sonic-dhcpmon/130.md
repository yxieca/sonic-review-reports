## Summary

The PR adds source-owned Bazel binary, runtime/debug archives, Debian-recipe metadata and a utility test for native AMD64/ARM64 Trixie. It preserves all ten daemon translation units and leaves their algorithms, database/counter behavior, locking and packet-processing source unchanged.

The one production-adjacent edit is a paired JsonCpp include-path correction: `<json/json.h>` plus the original Make compiler's `-I/usr/include/jsoncpp`. The utility test links the real `util.cpp` and supplies correctly typed application globals, including the existing `std::mutex`; it deliberately avoids the DB/dual-ToR path. Runtime/debug and metadata checks are meaningful, but remain distinct from a full daemon/image/live-traffic qualification.

## Source assessment

### Paired include-path change and source parity

[Header](https://github.com/sonic-net/sonic-dhcpmon/blob/65b99647b87eb0955009310c531d0fadcb840c60/src/util.h#L1-L20) · [Make compiler](https://github.com/sonic-net/sonic-dhcpmon/blob/65b99647b87eb0955009310c531d0fadcb840c60/src/subdir.mk) · [Bazel binary](https://github.com/sonic-net/sonic-dhcpmon/blob/65b99647b87eb0955009310c531d0fadcb840c60/BUILD.bazel#L1-L28).

The changed include spelling resolves the same Debian path once the original Make compiler gains its matching include directory. JsonCpp's selected Bazel source exposes `include/json` through its public include root. The new binary lists the same ten production `.cpp` files, retains optimization/debug flags and explicit pthread support, and uses pinned target libraries. Source parity is not a claim that differing compiler/dependency configurations can never affect runtime behavior; no actual incompatible configuration was demonstrated here.

The exact BASE/HEAD production source remains unchanged. Inherited utility/parser/counter/packet limitations were not promoted into new blockers merely because the build now packages that source another way.

### Real utility source and mutex boundary

[Test](https://github.com/sonic-net/sonic-dhcpmon/blob/65b99647b87eb0955009310c531d0fadcb840c60/tests/util_behavior_test.cpp#L1-L50) · [existing lock](https://github.com/sonic-net/sonic-dhcpmon/blob/65b99647b87eb0955009310c531d0fadcb840c60/src/util.cpp#L13-L20) · [production owner](https://github.com/sonic-net/sonic-dhcpmon/blob/65b99647b87eb0955009310c531d0fadcb840c60/src/dhcp_mon.cpp#L53-L66).

The standalone target links production `util.cpp`, not a copied checksum/JSON implementation. Its fixture defines `std::mutex mux_table_lock` and the required pointer/state globals because the daemon's production owner is not linked into that standalone binary. Those types match the real extern contract.

`dual_tor_mode=false` means `intf_is_standby` does not take the lock or call the DB table. This is correctly documented; the test proves linkage and pure utility behavior, not production shared-connection concurrency. The 10 authored groups check checksum lengths zero through 65, carry folding, IPv4/IPv6 pseudoheaders and zero encoding, integer/JSON boundaries, address formatting and counter keys/legacy serialization. Assertions remain enabled in optimized builds.

### Runtime, debug and package ownership

[Runtime and metadata](https://github.com/sonic-net/sonic-dhcpmon/blob/65b99647b87eb0955009310c531d0fadcb840c60/BUILD.bazel#L29-L70) use the exact published Build Infra and source-built Common providers, plus the shared locked `dhcpmon_debian` graph. The native test wrapper stages declared target loader/libraries rather than relying solely on a host installation.

The actual pinned runtime/debug producer, compiler/sysroot and metadata/helper source were inspected. The artifact checker requires one expected root-owned payload, native ELF machine/class, matching build ID, detached DWARF and exact debuglink filename/CRC. The metadata checker binds source control/changelog and runtime digests, validates package architecture/version, and checks each daemon `DT_NEEDED` basename has a target package provider named in generated `Depends`.

No produced ELF/archive was rehashed, extracted or loaded by this review. Some dependencies include transitive Boost runtime packages; a passing metadata check does not justify claiming those libraries are statically linked merely because no separate Boost entry appears in the owner call. Generated target-provider and actual ELF validation remain attributed to the hosted executor.

## Nonblocking notes

### N1 — Correct the registry name

[README introduction](https://github.com/sonic-net/sonic-dhcpmon/blob/65b99647b87eb0955009310c531d0fadcb840c60/README.bazel.md#L1-L8) says “canonical securely1g registry,” whereas [`.bazelrc`](https://github.com/sonic-net/sonic-dhcpmon/blob/65b99647b87eb0955009310c531d0fadcb840c60/.bazelrc#L1-L7) selects `sonic-net/sonic-bazel-registry/main`. Change the prose to the SONiC registry name. This is a documentation correction, not wrong runtime registry selection.

### N2 — Add an explicitly unaligned accumulator input

`tests/util_behavior_test.cpp` calls `checksum_accumulate_words(bytes.data(), n)` at one starting address for the 0–65 length sweep. The source loads individual bytes and no alignment defect was found, but an `alignas` backing array with `data()+1` would deliberately protect unaligned-buffer behavior. Keep the case on the byte accumulator rather than creating misaligned `iphdr*` objects. This can follow separately.

### N3 — Protect the new checkers' rejection paths

The source CI exercises successful artifact/metadata checking, but contains no dedicated rejection tests for `.github/scripts/check_dhcpmon_artifacts.py` and `check_dhcpmon_metadata.py`. Optional controls should reject extra/wrong/nonregular payloads, wrong owner/mode/machine, mismatched build IDs/debuglink CRC, wrong runtime/control hashes, unresolved fields and absent target providers. Test the existing helpers with inert inputs; no duplicate daemon or broad native campaign is required.

### Q1 — Keep provider verification claims proportional

The provider loop establishes that a package in `Depends`, with an acceptable control architecture, contains a file whose basename matches a daemon-needed library. It does not independently establish that provider's ELF machine/SONAME, full symbol ABI or a versioned alternative's installation. The underlying metadata generator is stronger and derives actual Debian controls from staged target libraries.

No supported selected counterexample showing false acceptance was demonstrated. Clarify that the light checker supplies provider-name consistency, or add separately scoped strengthening if complete provider-ABI verification is promised. This is a question/limit, not a dependency-resolution blocker.
