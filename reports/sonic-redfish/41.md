## Summary

The bridge now seeds Switch-Host and derived chassis power as Unknown until a recognized host-state row exists. Patch0009 makes bmcweb omit `PowerState` and report `UnavailableOffline` for that explicit unknown state rather than guessing Off. Runtime unknown/unrecognized updates retain the last recognized state; that different startup/runtime rule is documented.

The subscriber watches all `LIQUID_COOLING_INFO|*` rows and replays both host state and leak discovery after subscriptions are active. New sensors are posted to the I/O owner, created transactionally, registered with ObjectMapper, and announced once when their initial state is not OK. Sensor hardware faults affect individual GET availability/health, while confirmed leak severity remains visible.

Current source also corrects the earlier unsafe-looking recovery event classification and restart-test process lookup. The already-leaking fault-event gap and aggregate rollup are not newly worsened by this patch; both were explicitly accepted for follow-up in the current human review. The report does not repackage those known gaps as new blockers.

## Source-supported fixes

### Unknown Switch-Host state and startup subscription window

[Host-state mapping](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/include/host_state_mapping.hpp) returns Unknown for an absent or unrecognized initial row, maps recognized power/status combinations, and derives the matching chassis Unknown state. [StateManager](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/state_manager.cpp) applies changes through the I/O owner.

The [subscription callback](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/bridge_app.cpp#L480-L515) calls `syncHostState` and `syncLeakSensors` after all key subscriptions have been established and before the subscriber drains subsequent notifications. A host row written between initial read and subscription is re-read; a later write is a notification. [UpdateEngine](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/update_engine.cpp) now handles the host key regardless of which field generated the callback, so a row containing only recognized `device_status` is not rejected by an obsolete power-field gate.

[Patch0009](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/patches/0009-Report-unknown-Switch-Host-power-state-until-bmcctld-publishes.patch) has unique matching source context in the Makefile-selected bmcweb revision. Its Unknown branches set unavailable state without adding a power-state guess. Exact-context inspection/substitution was performed without compiling or executing bmcweb; this is not a full native patch/build test.

Deletion/reconnect/current-state lifetime beyond the new startup scenario remains bounded by the existing subscriber grammar: it handles HSET notifications, not a general resource-deletion lifecycle. No newly introduced deletion recovery guarantee is invented.

### Faulted detector GET and recovery events

[LeakSensorInfo](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/include/types.hpp#L153-L192) maps a faulted sensor reporting `leaking=No` to Unavailable, while retaining Critical/Warning for a leak it still reports. [Individual GET status](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/rmc-events/lib/leak_detection.hpp#L84-L126) considers both DetectorState and Functional: unavailable/empty/nonfunctional state becomes `UnavailableOffline`, with at least Warning health and any higher known leak health retained.

The [event monitor](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/rmc-events/src/leak_detector_monitor.cpp#L158-L233) no longer emits an OK status notification when recovering into an active Critical/Warning leak. Critical recovery emits Critical; OK recovery emits OK; Warning recovery does not claim an OK health change and still sends its leak notification. Current tests cover both recovery-to-Critical and recovery-to-Warning.

### Late sensor discovery, registration and exception cleanup

The pattern subscription and [leak synchronization helper](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/include/leak_sensor_sync.hpp) distinguish Create, Update and no-change from actual object presence and tracked detector/hardware health. Updates are posted to the I/O owner rather than mutating D-Bus registration from the subscriber thread.

[DBusExporter](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/sonic-dbus-bridge/src/dbus_exporter.cpp#L294-L456) removes partially added interfaces and cached map entries when creation fails. A late object uses `initialize(true)` to suppress initial property-change announcements, then ObjectMapper registration precedes its one intentional DetectorState announcement. The exact pinned sdbusplus implementation confirms `initialize(true)` suppresses per-property signals and a same-value `set_property` does not emit a change.

Startup/restart reannouncement is intentionally different: every detector reannounces current state. The human discussion explicitly accepted this safety-oriented tradeoff rather than adding a persistent sent-alert ledger. No repeat of that accepted concern is requested.

### Restart helper process identity

The current [restart helper](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/tests/redfish-api/framework/restart_bridge.py#L87-L142) uses the State.Host bus owner's PID and validates the executable before signalling. It no longer relies on a17-character executable matching a15-character process-name field. Lookup error and absent owner are distinguished.

Coordinator-only execution of the **extracted Python identity helper**, with fake owner/readlink functions, accepts the expected executable and deleted suffix, rejects a different executable, and returns no PID for no owner/exited process. No actual process lookup, signal, D-Bus query or live endpoint request was executed. Native restart and BMC results remain reported validation, not this review's own tests.

## Q1 — fault/recovery while already leaking remains a nonblocking event gap

A Critical/Warning detector that changes only hardware Functional status retains its DetectorState string. UpdateEngine notices the tracked health change and writes Functional, but sdbusplus suppresses the same-value DetectorState signal. The leak monitor matches only the LeakDetector interface and therefore does not observe the OperationalStatus-only signal. Individual GET correctly changes availability, while the event stream can remain silent.

The exact base has the same already-leaking mapping, update ordering and monitor match. This PR improves individual GET and faulted-not-leaking events without worsening that inherited branch. A broad description that every fault/recovery emits ResourceStatusChanged is therefore too strong, but does not establish a newly introduced safety failure.

[The existing reopened thread](https://github.com/sonic-net/sonic-redfish/pull/41#discussion_r4583528004) and current human approval explicitly leave this nonblocking for follow-up. A future fix should monitor/reconcile Functional changes without inventing false OK health or losing the active leak. Keep it tracked; do not duplicate the target feedback.

## Q2 — aggregate health rollup remains an inherited follow-up

[LeakDetection aggregate GET](https://github.com/sonic-net/sonic-redfish/blob/2248d794ffa1989d3c86ae5c88c57d2a9a5fa25b/rmc-events/lib/leak_detection.hpp#L161-L200) still reports its own Enabled/OK status without deriving detector rollup. This is unchanged from base, while individual detector status is now improved.

The existing human review asks for schema-appropriate `Status.HealthRollup` rather than conflating resource Health with child health, and expressly accepts a follow-up instead of blocking this PR. Preserve that [discussion and follow-up issue47](https://github.com/sonic-net/sonic-redfish/issues/47). No actual RMC failure or thermal mitigation consequence is inferred.

## N1 — four-field MessageIds are correct but wire-visible

Events now use four-field forms such as `ResourceEvent.1.3.ResourcePoweredOn` and `Environmental.1.1.LeakDetectedCritical`. The exact selected bmcweb `event_matches_filter.hpp` requires four components for RegistryPrefixes parsing. The former five-field form fails that parser; the in-repository descriptions/cases are updated.

External subscriptions/tests matching the former full MessageId need coordinated updates. The author reports an updated sonic-mgmt/BMC run, but that does not prove every consumer is updated. This is a compatibility/release-note concern, not a source reason to restore invalid registry syntax.

Deprecated ThermalSubsystem OriginOfCondition URIs remain deliberate backward compatibility; canonical and deprecated routes are served. The human discussion explicitly deferred changing the event URI until consumers are ready. Nested GET latency optimization was also accepted for measured follow-up. Neither is reintroduced as a blocker.
