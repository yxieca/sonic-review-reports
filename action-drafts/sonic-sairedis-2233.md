## Request changes

**Restore the existing non-ASAN fortification policy in the Bazel build.** The exact baseline [Debian recipe](https://github.com/sonic-net/sonic-sairedis/blob/22550fa427562f31d3bde5c66e622a437a5f6496/debian/rules#L19-L24) explicitly adds `-U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=3` for non-ASAN compilation. The selected [GCC toolchain flags](https://github.com/sonic-net/sonic-build-infra/blob/77ef625a4ddafc8cdc15f3cc6aee31eabac8a5de/toolchains/args/BUILD.bazel#L86-L112) instead define `-O2 -D_FORTIFY_SOURCE=2`. The new [C++ production flags](https://github.com/sonic-net/sonic-sairedis/blob/4ea34ffd1a6cf91fa4e86a80529224e7e7698f5e/bazel/common.bzl#L13-L85), [C metadata target](https://github.com/sonic-net/sonic-sairedis/blob/4ea34ffd1a6cf91fa4e86a80529224e7e7698f5e/meta/BUILD.bazel#L37-L60), and separate [Python-extension compilation](https://github.com/sonic-net/sonic-sairedis/blob/4ea34ffd1a6cf91fa4e86a80529224e7e7698f5e/pyext/BUILD.bazel#L50-L82) do not restore the component's level-3 override. Thus the supported default native Trixie AMD64/ARM64, VS, Python-3, non-ASAN path loses that existing hardening policy. Please carry the non-ASAN undefine/redefine into the relevant compilation paths after the toolchain definition, while retaining the existing ASAN exception. This is a source-defined hardening-policy discrepancy, not a reproduced exploit or evidence that other hardening is absent.
